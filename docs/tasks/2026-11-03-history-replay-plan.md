# 数字孪生时光回溯：推荐方案与实施计划

> 2026-11-03 可行性修订。本文是待实施方案，不表示历史采集、状态内核或回放接口已经实现。本轮仅修订方案与任务记录，不修改业务代码、不运行服务或测试。
>
> **结论：总体方向有条件可行，但不能直接以原排期承诺生产交付。** 必须先通过“真实来源与初态接续、完整物流最小闭环、持久化与查询边界”三个准入点，再扩展到全部设备与约定规模。缺少权威基线、必要业务脚本尚未迁移或容量不足时，明确阻塞完整回溯上线，不降低已确认范围。

## Context

为已发布的数字孪生 Web Viewer 增加完整历史运行状态回放，用于故障复盘和过程追溯。用户已确认：

| 项目 | 已确认要求 |
|---|---|
| 回放范围 | 设备运动与状态、动态设备、货物生成/销毁/流转/入库、告警 |
| 历史基础 | 尚未保存满足需求的历史，需要新增持续采集 |
| 配置入口 | 编辑器工具栏的“时光回溯设置”，在编辑器内完成配置、预检、发布衔接及后台采集状态管理 |
| 回放入口 | 发布后的 Web Viewer；本次不新增编辑器专属回放面板，也不把编辑器作为持续采集进程 |
| 留存跨度 | 数月或更久，最终天数需结合容量确定 |
| 规模 | 1000 台以上，每秒多次上报 |

本轮仅提供方案和计划，不修改业务代码、启动服务、运行测试或操作数据库；现有未提交改动完整保留。

## 一、总体建议

采用 **后台持续采集＋不可变事件归档＋同版本业务状态投影＋完整检查点＋Viewer 独立回放会话**。在现有 CentralDataPlatform 承载采集配置、历史查询和版本管理；从 Babylon 运行时抽出无渲染依赖的 TypeScript 业务状态内核，由受监督的服务端 Node worker 和 Viewer 共用，避免用 Java 再写一套货物流转规则。

这不是视频录像，也不是把 MQTT 消息重新发布到生产 broker。回放重建的是平台在约定时间轴上可观测的业务状态：有位置观测时按观测恢复，采样间运动按固定版本规则插值，并标明推算/未知。不能承诺补回采集之前的数据、未被上游报告的物理过程，或逐像素复现当年某个浏览器画面。

完整业务状态是最终交付要求。阶段性设备回放只是中间里程碑，不以“设备能动起来”替代货物、库位、告警等完整闭环。

### 编辑器配置入口与生效流程

**编辑器负责配置与发布，后端负责持续采集与存储，Viewer 负责只读回放。** 不要求使用者另外进入数据平台管理页或手工修改 JSON/YAML 完成场景级回溯配置；服务器安装、存储容量和凭据部署仍是基础设施前提，不由场景文件承载。

#### 入口与配置内容

在 `Toolbar.tsx` 现有 MQTT/发布工具附近增加 **“时光回溯设置”**；由 `EditorLayout.tsx` 复用 `LazyEditorDialog` 打开独立配置对话框，不继续把整套新表单塞进 Toolbar。发布弹窗展示该配置摘要和预检结果，并提供返回设置的入口，不维护第二份可编辑配置。

| 配置分组 | 编辑器中提供的内容 | 边界 |
|---|---|---|
| 功能与项目 | 启用 Viewer 回溯入口、当前工程/场景、目标项目、历史服务能力与连接状态 | 复用现有数据平台项目绑定，不重复填写独立平台地址 |
| 数据与初态 | 选择已有 MQTT/Fetch 绑定、服务器采集源引用、设备身份映射摘要、库存/货物基线来源 | MQTT topic/字段映射复用已有配置；发布时解析最终有效来源并锁定摘要，避免两份配置漂移 |
| 留存与资源 | 期望保留天数、可选服务器存储策略、容量估算、允许的资源/检查点策略 | 后端给出可选策略、上限及有效值；不让前端直接填写磁盘路径、对象存储密钥或任意服务端代码 |
| 回放显示 | 默认打开的时间范围、默认倍速、是否显示关键事件标记 | 仅影响 Viewer 展示；不能借此启停后台采集 |
| 发布与采集状态 | 本地草稿/已发布/已应用版本、实际采集状态、完整基线状态、投影延迟、可回溯起点及缺口 | “已保存”“发布成功”“已应用”“正在采集”“完整可回溯”分别展示，不能用一个成功提示混淆 |

默认复用既有设备/货物/告警范围，不新增会悄悄削减“完整回放”的抽样开关。未绑定平台或离线时可编辑、保存非敏感草稿；服务端预检、应用、启停按钮说明禁用原因。

#### 保存、发布和远端控制

推荐首次启用路径：**编辑器配置 → 保存场景草稿 → 服务端预检 → 发布场景版本 → 编辑器显式“应用并启用采集” → Viewer 查询与回放**。

已有有效发布版本时，纯留存/资源策略变更使用编辑器中的 **“预检 → 应用采集策略”**，不强制重发场景包，也不改变原采集启停状态；只有数据合同或场景逻辑变化才重新发布。

- 草稿按场景保存，拟新增可选 `sceneSettings.historyReplay`，其内容为功能/显示设置、来源引用及申请策略；沿用现有 Store、命令和场景保存/校验链路。“应用到场景”只产生一次可撤销修改并标记待保存，“保存场景”复用现有磁盘保存流程，写盘失败不得显示已保存。旧场景缺省关闭，取消未应用表单不修改场景，重新打开读取已应用配置。
- 区分“场景内容待发布”和“采集策略待应用”：修改 MQTT/Fetch 来源或映射、设备绑定、场景逻辑/业务脚本等数据合同后，旧预检失效，必须创建并激活新发布版本；仅调整留存、服务器资源策略或暂停/恢复时，可对已有成功发布基线在编辑器内重新预检并显式应用，不强制重打 SOURCE/DIST。所有相关变更都使原预检失效，但不都要求重新发布；未提交生效前，服务端仍运行旧有效配置。
- 服务器分别维护项目级采集策略 revision 与场景发布绑定 revision，两者共同决定有效配置；场景文件里的申请值不是已生效值。明确共享采集任务归属，变更/暂停时展示受影响场景，不能因复制/导入场景重复启动或误停共享任务；应用须同时核验两类预期 revision。撤销/重做仅作用于本地场景草稿，不隐式回滚已应用的服务端策略。
- 编辑器对比本地声明、目标发布版本和远端有效 revision；切换项目必须重新解析来源/策略引用，未映射的引用阻止应用，不把旧项目的引用当成新项目的权限。
- “保存草稿”、普通场景加载、普通运行预览和单纯发布均不自动启停采集。发布预检验证身份、来源、基线、服务能力、容量和授权；发布成功后由明确的编辑器操作激活对应已发布版本。
- 已核实 `electron/ipc/digitalTwinPublishService.ts:443–453` 会在上传/提交之前保存现有大屏嵌入运行配置，正式版本提交在 `:625–630`。新的回溯候选声明只能随发布 manifest 保存，**不得借用这次提前写入就激活采集或更改有效策略**；服务端有效历史策略独立于通用 `configJson` 整体覆盖写入，避免旧发布请求把已生效策略覆盖回旧值，不顺带改造现有大屏 Origin 业务。
- 来源引用必须固定数据源修订、字段映射版本和发布基线摘要；应用时再次核对，防止“预检通过后来源被修改”。服务端能力/配额低于已要求的完整精度、留存或采集目标时阻止应用，不静默降采样或缩短保留期。
- 将启用/策略更新作为幂等后台任务处理，包含 `requestId`、两类预期 revision、已发布版本/数据合同摘要。候选准备期间保持原有效配置；提交点需同时记录生效策略/绑定 revision、基线和切换游标，确保新状态可读取后再对外宣布生效。提交前可取消候选，提交后取消不能冒充回滚；请求超时先查询原任务，并沿用原幂等键重试，不重复建立采集器。
- 已有采集继续使用旧有效配置。新版本发布成功但配置应用/初始化失败时，展示“已发布，采集配置未生效”，不停止旧采集、不把新版本宣称为可回溯；编辑器可从原任务状态重试或取消未生效候选。
- **发布地址切换与采集激活不是同一事务。** 当前中台 `commit/rollback` 会部署并切换 `onlineVersionId`，所以即使旧采集仍正常，新打开的稳定地址也可能已加载新布局。声明启用回溯的 Viewer 在启动、返回实时和发布回滚后，都必须以自身包身份核验 `publishedVersionId`、有效 `bindingRevision`、投影与场景资源版本；不匹配时停在“待启用／版本不匹配”，不启动业务驱动、不将旧投影套在新布局上，也不静默回退到直连 MQTT。编辑器发布摘要须提示这个等待窗口；原有未启用回溯场景不改变行为。
- DIST 生成早于服务端分配正式版本 ID，不能要求生成时填写尚不存在的 `publishedVersionId`。可复用包内 `cacheRevision` 作为包身份，由提交阶段登记 `(projectId, cacheRevision) → publishedVersionId/manifestDigest`；它目前是随机标识，不是内容摘要或授权令牌。新握手验证该映射后才解析有效绑定；源文件/模型与状态就绪后按切换游标接入。仅普通发布回滚不自动回滚采集策略，仍需显式激活对应版本并通过同样核验。
- 提供明确的“暂停采集/恢复采集”操作，暂停会新增历史缺口并先提示影响；暂停不删除已保存历史。缩短留存属于潜在历史删除，展示受影响区间并单独确认，不与普通保存或应用静默捆绑；本功能不提供一键清空历史。
- 服务端预检必须验证**服务器**能访问的 broker/归档/基线来源；编辑器本机 MQTT 测试成功不能代替它。服务器 TCP/TLS 连接配置和 Viewer WebSocket 地址不得直接混用。
- 采集控制通过受控 preload/IPC/API 桥接与项目级管理授权；现有发布 `targetToken` 只是临时目标上下文票据，不能充当长期管理凭据。Viewer 只收到脱敏后的查询入口、已应用配置/版本标识和展示选项，不获得管理权限或采集凭据；SOURCE/DIST 都不得嵌入服务器密钥。当前中台匿名认证仍不能承担这些权限，需沿用本方案明确的可信网关/限定作用域授权边界。
- 关闭编辑器、关闭设置弹窗或关闭 Viewer 不会停止后台采集；弹窗关闭仅释放其状态订阅，后台任务结果可再次查询。

## 三、推荐架构与数据流

### 1. 独立历史采集：浏览器关闭也持续工作

新增历史采集配置和服务，不借用流程运行、浏览器在线或“发布 Viewer”来隐式启动采集。

- 订阅 Viewer 实际消费的最终 MQTT topic。若数据编排改变了原始消息，记录其最终输出流，不能错误地以变换前输入替代。
- 原始 topic、payload 字节及接收元信息先进入可恢复的追加日志，再做解析、过滤、去重和状态投影；畸形消息也保留原始证据和拒收原因。
- 复用现有 Paho 连接配置能力，但不能沿用 latest 的覆盖缓冲或发送后入库流程。
- 每个采集分区只有一个有效写入者，以持久游标和代际隔离重复写入者。优先按项目/完整物流关联域分区，不把存在货物交接的设备随意拆成互不一致的分区。
- 采集进程重启、连接中断、磁盘满、归档失败、解析失败均产生可查询的质量状态。队列满时明确背压或记录缺口，不静默丢弃后仍报告“完整”。

完整性承诺以“上游已发送且满足约定交付条件的事件”为边界。需要持久 MQTT 会话、稳定 clientId、合适的 QoS、可验证的确认时机及 broker 保留/补发能力；QoS 0 或无法补发的上游不能承诺零丢失。确认不能早于约定的持久化完成；本地 WAL 耐进程崩溃不等于耐整机/磁盘故障，后者需复制或备份及明确 RPO。

### 2. 同一套可序列化业务状态内核

新增纯数据内核 `TwinState`，把设备/货物流转的状态转换从 Babylon 对象操作中分离。

- 输入是归一化事件、已锁定的场景逻辑配置、显式时间推进；输出是业务状态及渲染变化，不依赖 DOM、WebGL 或网络。
- 复用现有协议解析、字段绑定和设备规则，保留当前“整帧字段替换”“报警点位保留”“逐消息心跳”等不同语义，不顺手统一成另一套业务规则。
- 同一内核发布为可版本化的构建产物，供 Viewer 与服务端 Node 投影 worker 使用。中台 Java 负责接入/存储/API，不重复实现六类设备和货物流转算法。
- 场景发布时生成逻辑清单：身份绑定、设备参数、库位、输送链路、几何派生的逻辑尺寸/锚点、生成器规则。服务端不靠加载 Babylon 网格猜邻接关系。
- 外置脚本若影响业务状态，必须改为显式状态、可快照/恢复、受注入时钟驱动；仅有渲染用途的脚本作为渲染适配器。不能在服务器无约束执行发布包任意脚本；需要受控能力、资源限制及隔离。
- 逻辑实体的存在不取决于 GLB 是否加载完。异步渲染只是追赶已经成立的业务事实，避免快慢电脑回放出不同货物流转。
- 服务端投影是启用回溯版本的业务状态权威；Viewer 应用状态并计算只读展示位姿，不再同时调用旧驱动二次生成货物、交接或判定 TTL。共用内核不等于同一个状态转换在前后端重复提交。
- 动态实体 ID 从上游稳定身份或已记录事件/生成计数确定，随机数种子和计数必须进入检查点。匿名货物只保证系统内生命周期可重复识别，不能捏造其真实条码或跨来源对应关系。

**共用内核须有明确的写入权与时间推进合同：**

- Node 投影进程独占业务 `applyInput/advanceTo`，生成提交的状态变化；Viewer 复用状态 schema、解码/应用器及 `samplePose(state, T)` 等只读运动求值，不再次根据遥测生成/销毁货物或重做交接。不得把整套旧 `*Driver` 同时接在历史状态后面。
- MQTT、业务 Fetch 完成、初始化/配置控制以及逻辑推进记录由关联域的同一顺序器分配游标。无消息期间也记录可恢复的推进边界；墙钟只驱动在线调度，不直接参与离线恢复。迟到输入以新的有序观测记录进入，不插回已经发布的过去。
- 内核版本固定“同刻输入/到期任务的顺序、逻辑步长或解析运动规则、浮点精度/舍入方式”。定时队列和下一截止时间进入检查点；恢复时按同一规则推进，不用 seek 请求的到达时间、渲染 FPS 或播放倍率计算业务变化。重启后的时间跳跃必须结合连续性状态处理，不能跳过 TTL、脉冲、交接等离散事件。
- 运动记录起点、目标、阶段、轨迹参数及有效时间区间，而非每个渲染帧为全部设备写一份位姿。仅改变展示采样率不损失输入；但影响归属、到站、生成/销毁的中间变化必须持久化，不能用末帧覆盖。不能解析推进的脚本使用版本锁定的固定逻辑步长，其成本计入容量预算。

**Fetch 库存不是单纯的“响应 JSON 输入”。** 当前 `SceneLocatorFetchController` 还负责全量/单排请求的逐排代际仲裁、格口抑制、设备保留货物及单排响应后的清算，必须一起抽入状态内核：

- 内核产生可持久化的库存查询意图，后台只读适配器执行；记录 `requestId/attemptId`、来源合同、全量/单排作用域、各排请求代际、发起/完成时间、成功/失败及响应引用。传输返回全量记录不改变逻辑请求的单排作用域。
- 收到结果后按当时有效代际决定哪些排可应用，将库存更新、解除瞬态抑制和清算设备保留货物作为同一业务提交。被更新请求取代的旧响应保留证据但不覆盖新状态；持久保留格口不能当作瞬态抑制一并清空。
- 检查点包含逐排最新请求、待完成查询意图、瞬态/持久抑制集合及待清算 `cargoId` 关联，不序列化 Promise、AbortController 或 Mesh。只恢复最后一份库存 JSON 会丢失这些信息。
- 活跃 worker 重启时，已持久完成的结果按游标恢复；仍挂起的只读意图可按当前代际取消或重新尝试，并记录新的 attempt。新响应的观测时间不得倒填到原请求时间。seek 仅应用历史上已提交的结果与动作，绝不重新请求当前库存；过期 worker 的迟到回调按写入代际拒绝。
- 原有 Fetch 若调用可能含发送节点的流程，必须先提供经过确认的只读取数适配；影子投影及历史查询不能额外执行这种流程。后台采集、浏览器实时和影子投影应共享已采集输入，不各自重复触发业务取数副作用。

具备回溯能力的场景版本，其实时业务视图也应接到这套 canonical 状态投影，避免实时与历史长期保留两套算法。迁移顺序是：固定输入下影子投影与业务记录对照 → 按场景切换统一实时状态来源 → 开放该版本的完整回溯。完整保证起点 `T0` 必须同时满足有效初态、连续采集、版本锁定和统一状态链路；采集器上线时间不自动等于 `T0`。未启用历史的原有场景保持当前行为；这是明确的产品能力配置，不是掩盖不完整实现的降级开关。

### 3. 完整初始基线、检查点与派生记录

检查点保存的是可继续推演的业务状态，而不只是设备最后一个 payload：

| 状态类别 | 必需内容 |
|---|---|
| 遥测 | 身份、previous/current、有效心跳时间、排序/去重状态、连接纪元 |
| 运动 | 当前位姿、目标、运动阶段、插值起点/开始时间/持续时间、相关设备联动状态 |
| 动态设备 | 生成器、动态实例、身份映射、最后心跳、TTL 截止时间 |
| 货物与仓储 | 稳定 cargoId、容器/任务身份、生成来源、宿主/库位、在途交接、排队/脉冲、自驱状态及销毁记录 |
| 告警 | 保留点位、活跃集合、触发/解除时间、求值水位与边沿状态 |
| 其他业务输入 | Fetch 库存、逐排请求代际/作用域、挂起查询意图、瞬态/持久抑制、待清算货物关系；有效配置与来源快照版本 |
| 一致性 | 状态 schema、投影器版本、场景/脚本哈希、已应用日志游标、逻辑时间、内容校验和 |

**首次启用不是先抓一个全量、然后再订阅。** 在用户显式启用后，先建立可恢复的增量接收，再读取权威全量并对齐其来源游标；准备期只显示“采集中／初态未对齐”。满足以下条件才建立完整起点 `T0`：

- 基线来自 WMS/WCS/设备或其他已确认的只读权威接口，包含既有库存、持货设备、在途任务及必要运动阶段；最新位置与库存列表不一定足够恢复中途交接。
- 基线携带来源的快照修订与增量边界；已有跨源一致性协议则直接复用，否则记录各源边界向量及对账结果，不能把几个不同时间的 HTTP 响应冒充同一原子快照。来源没有快照/增量衔接能力时，需业务方提供可证明的对齐基线；不能仅凭本机时间戳或 retained 消息宣称对齐，也不擅自要求生产停机。
- 先应用边界内的全量，再按确定顺序追赶边界后的缓冲事件；重叠事件按来源版本/事件身份处理。检查单一货物宿主、库位占用与未完成交接一致性后，提交基线与对应游标。准备失败保留旧有效投影；首次启用失败不得生成空库“完整”基线。
- 缺少必要来源时仍可明确保存原始证据，但不得宣称完整回溯；原始采集起点、初态就绪点与完整回溯起点分别记录。

**断档后重新建立完整性。** 暂停、broker 补发失败、必需输入丢失等会关闭当前完整区间，后续检查点继承未对齐状态。恢复连接不等于恢复完整状态；必须证明缺失输入已按协议补齐，或建立覆盖设备、动态实体、库存/在途货物及必要告警状态的新基线和 `T1`。新基线提交后开启新的投影代次；变化查询返回 `STATE_RESET_REQUIRED`，实时和历史消费者重新加载全态，不能将新库存作为几条普通增量接在旧状态后。同一场景发布版可以重新对齐，无需重发场景。无法补齐的过去持续标为缺口，不能拿恢复后的库存倒填此前货物流转，也不能让旧检查点跨过缺口后继续被标为完整。

检查点在明确的事件/逻辑推进边界提交。使用 `StateCursor = { projectionId, stateRevision }` 对外接续，`projectionId` 唯一标识绑定采集关联域、场景发布版、配置摘要和状态内核版本的一个**投影代次**；其检查点另外保存 `inputCursor = { captureDomainId, captureEpoch, offset }`、`logicalTime`、定时任务队列及去重状态。一个关联域内统一排序各来源，不直接比较不同流的 offset；跨独立关联域的业务交接需要先合并其一致性边界，首版不隐式支持跨分区事务。大整数均按字符串传输。

**分别发布水位，不让冷归档与周期检查点阻塞实时显示：**

| 水位 | 提交前提与用途 |
|---|---|
| `capturedThrough` | 原始输入已达到约定持久性，可以确认接收；不表示已经投影 |
| `committedStateCursor` / `committedThroughTime` | 已持久提交的业务变更批次及逻辑时间；实时只能读取其完整批次 |
| `checkpointCursor` | 可完整恢复且校验通过的检查点位置，不必等于最新状态 |
| `archivedThrough` | 对应不可变归档块及索引已完成，可用于冷历史恢复和安全回收热日志 |
| `queryableThrough` | 查询服务持有兼容基线及其后连续、可读的热日志或冷归档；同时公布缺口，不能仅由最大时间戳推断完整 |

原始输入、业务变化和索引不能假设跨 Java、Node、文件与 MySQL 有同一事务。实现为可重试的提交协议：先写不可变批次并校验，后在元数据事务中核验写入代际、登记输入范围和新状态游标；只有提交记录可见的批次才对外返回。失败时重试相同批次身份，不产生新的重复业务事实；孤立未提交文件不供查询，按受控回收清理。旧写入者的迟到提交必须被拒绝。实时流读取已提交的热变化日志，不等待下一次冷归档或全量检查点；若持久存储不可用则显示滞后/不可用，不自动混回浏览器直连 MQTT。

首版优先使用**周期完整检查点＋其后的不可变业务变化日志**，并明确一次恢复所需的最大时间/字节预算。只有真实状态体积证明全量成本不可接受时，才加入分块复用或有界增量检查点；此时必须同时实现依赖闭包保留。周期根据设备、货物、库位状态总量及恢复预算确定，不先承诺固定一分钟或几百毫秒定位；检查点写入量按“实际序列化大小 × 每日次数”单独预算。

### 4. 服务端按时刻恢复，浏览器只处理短窗口

`asOf(T)` 从兼容版本的检查点恢复，应用已提交的业务变化至 T，再依据该时刻有效的运动描述求展示位姿；不在查询时另跑一条可改变货物归属的业务投影。返回 `requestedTime`、`resolvedTime`、实际游标、版本和质量。T 超过可查询水位、处于缺口或早于有效基线时返回明确状态；不悄悄钳制到几秒前的检查点并标成 T。

- 浏览器只请求目标时刻状态及相邻短窗口的紧凑变化，不下载数月原始 MQTT，也不从当天零点重新演算。
- 服务端恢复任务使用独立于实时投影的有界查询 worker/队列，不能为大量拖动查询阻塞正在采集的关联域。请求取消需要传播到服务端；重试复用未过期的查询身份。
- 完整状态超过单响应预算时，`/state/at` 返回不可变 `snapshotId`、同一游标和分块清单，`/state/chunk` 按块读取；所有块校验完成后才安装。快照租约有过期与字节预算，不能逐页读取不断变化的实时 Map。若目标场景完整状态超出客户端支持上限，预检/打开时明确阻塞，而非截断实体并声称完整。
- 浏览器 Web Worker 负责解析/解码和状态准备；主线程分批建立渲染对象，完成必要资源与实体准备后再切换可见状态/时间标尺。逻辑上的一次提交不等于在一个帧里同步创建全部 Mesh。没有双场景显存预算时，使用冻结画面/加载遮罩过渡，不承诺原场景继续交互且新场景无成本瞬时替换。
- `/changes/query` 固定一次请求的 `toCursor` 和 `throughTime`，范围为 `(afterCursor, toCursor]`。单个状态修订含跨设备交接等原子业务变更，不能分页后只应用半个修订；超大修订可分片传输但组装后再应用。返回 `nextCursor`、`hasMore`、版本/缺口和字节预算；空响应不得推进到尚未提交的位置。
- 游标属于同一 `projectionId`；不匹配、已过期、跨版本或依赖缺失分别返回明确原因。游标过期时重新取完整快照，不能从“最接近的最新消息”接着播。每个会话的快照/日志租约都有 TTL 与上限，过期后允许受控清理；播放会话不能永久阻止留存删除。
- 提供有限预取与按版本/权限隔离的缓存；关键事件与生命周期变化不能为追求帧率而丢弃。倍速仅改变消费虚拟时间和展示采样率，不改变业务事件或逻辑推进步长。消费赶不上时进入 `buffering`，不假装达到目标倍速或跳过事件。
- 跨设备货物关系按一致状态提交；单设备详情过滤不应剪掉恢复整场业务所需的上下游事件。

## 四、时间、身份与版本契约

新增契约建议如下，字段名称为拟定名称，不表示当前已实现。

| 契约 | 关键字段 |
|---|---|
| `HistoryReplaySettings` | 场景内无密钥草稿：`version, replayEnabled, sourceBindingRefs, baselineSourceRef, requestedPolicy, viewerDefaults`；不包含正在采集等远端瞬时状态 |
| `CaptureConfigRevision` | 服务端有效策略与场景绑定：`projectId, captureDomainId, policyRevision, bindingRevision, publishedVersionId, sourceContractId, effectivePolicy, activationState`；变更核验对应预期 revision 与幂等请求 ID |
| `SourceContractSnapshot` | 不可变的数据源/接口/参数/字段映射/来源纪元规则快照与摘要、服务端凭据引用；不能仅保存指向可变数据源行的 ID |
| `HistoryEvent` | `schemaVersion, projectId, captureDomainId, sourceId, sourceContractId, captureEpoch, offset, inputKind, receivedAt, replayTime, payloadRef, transportMetadata`；MQTT 元数据保存原 topic/QoS/retain/dup，HTTP 元数据关联请求身份/作用域；源时间/序号可缺失，解析结果与拒收原因通过输入游标关联，不修改原始证据 |
| `ReplayManifest` | 按版本/投影列出的覆盖区间、缺口与原因、各类水位、初态与依赖状态、快照/窗口预算及接口能力 |
| `TwinCheckpoint` | `checkpointVersion, stateSchemaVersion, projectorVersion, publishedVersionId, projectionId, logicalTime, cursor, inputCursor, stateRef, checksum, completeness` |
| `ReplaySession` | `sessionId, projectId, projectionId, publishedVersionId, expiresAt, limits`；`generation/currentTime/mode/speed` 为客户端会话状态，数据请求携带 generation 以丢弃过期响应 |
| `StateChangeBatch` | `projectionId, fromRevision, toRevision, throughTime, inputCursor, changes, checksum`；每项修订记录自身 `revision/logicalTime` 与原子变更，支持准确截取到 T；跨版本不能复用游标 |
| `TemporalContext` | `sessionId, generation, mode, asOf, publishedVersionId, projectionId, cursor, readOnly`，供 Viewer 与业务面板统一使用；不替代服务端授权 |

原始输入按采集关联域保存一次，不按每个消费场景重复录制。场景/发布版通过各自 `projectionId` 消费同一证据；同一项目的多个场景不因此共享可变业务状态。`captureEpoch` 表示采集日志纪元，`deviceEpoch` 表示上游设备序号纪元，二者不能相互替代。

关键规则：

1. 默认按采集端有序观测重建“平台当时知道的状态”，保留设备源时间用于展示和诊断，不事后静默按源时间重排已发布历史。它不是对任意旧浏览器当时网络到达次序的保证。
2. UTC 毫秒用于跨系统时间，界面显式显示时区；播放推进使用单调逻辑时钟。源时钟漂移、采集端时钟回拨和重启用显式纪元/映射处理，原始时间不覆盖。
3. 数据身份至少为项目/采集源＋设备类型＋设备编号；`sourceId` 是稳定逻辑身份，不是随机连接 ID。设备序号重启必须有明确纪元规则，不能永远被旧大序号拒绝。
4. 日志 offset、业务 Long ID 和可能超出安全整数范围的源序号，在 JSON/前端用字符串。新的摄取 ID 不冒充上游事件 ID；相同 payload 可能是合法心跳，不能按内容哈希一律删除。
5. 场景、模型、脚本、绑定配置、逻辑清单和投影器版本共同锁定。不能拿今天的货架布局解释几个月前的数据；跨版本先关闭旧区间，再按新版本加载资源和基线，不在两种布局之间插值。
6. 有效历史持有资源引用，发布覆盖、资源清理与项目归档不得删除仍被保留期引用的资源。历史依赖缺失时明确阻止完整回放，不悄悄换成最新模型。

### 浏览器历史执行端的兼容策略

锁定旧投影器与 GLB 还不足以保证最新版 Viewer 能解码旧状态或调用旧脚本接口。**首版采用按历史回放 ABI 选择经批准的兼容 Viewer 执行产物**，不承诺最新版页面天然兼容所有旧状态：

- 发布清单记录状态 schema、投影器构建摘要、回放 ABI、兼容 Viewer 构建摘要及资源 manifest。相同 ABI 可复用经兼容确认的新 Viewer；不兼容时选择保留的兼容产物。执行产物、适配器和必要依赖纳入既有历史引用保留闭包，不能只保留数据和模型。
- 服务端 `/sessions/open` 核验授权和兼容矩阵后返回受控的历史启动入口与资源清单。浏览器切换到兼容产物时只保留一个运行场景，续接历史会话；不把全部旧脚本任意注入正在运行的最新版页面。会话能力不放在可泄露的永久公开 URL 中。
- 历史入口必须在初始化 MQTT/Fetch/业务脚本副作用**之前**识别 `mode=history` 并完成握手；不得把“直接打开旧 DIST 的普通 index”当成历史启动。其业务来源、逻辑配置和状态来自已锁定版本，不能再被按 projectId 读取的当前运行配置覆盖。
- API 部署地址、当前访问授权、停用决定与父页面 Origin 仍按现行安全策略解析，不因回放旧版本恢复旧权限或硬编码已失效地址。兼容产物若因安全原因停用，需提供保持该 ABI/状态语义的修复产物；在替代产物就绪前明确阻止受影响范围，不静默换资源或不安全执行旧包。
- 升级发布以“保留窗口内每个有效版本仍有可用兼容消费者”为门槛。状态语义修正另建投影代次及解释版本，不覆盖已公布的历史证据和旧投影；历史结果需能说明使用了哪个解释版本。

## 五、长期存储与容量

推荐分工：

- **MySQL：** 采集配置、采集纪元、版本绑定、覆盖区间、归档块索引、检查点索引、查询会话。不要把海量原始 JSON 逐条塞进当前业务表。
- **追加日志/WAL：** 有界持久缓冲、顺序编号、恢复游标；已确认写入不能仅存在内存。
- **不可变分块归档：** 原始证据、业务投影变化和检查点分开保存，按项目/日期/分区组织；各压缩块有时间/游标范围、记录数、压缩前后大小和校验和，避免一个超大 gzip 必须整日解压。
- **归档介质：** 复用 `StorageService` 边界；本地磁盘可用于开发和容量受控的环境，生产需落实足量持久存储、备份/恢复与访问隔离。现仓没有已验证的对象存储能力；若采用 S3 兼容归档，需要显式新增适配与部署，不假设 MinIO 已存在。
- **留存：** 配置化保留完整精度的原始事件、关键状态变化、检查点和关联版本；时间轴概览可降采样，但不能把几个月前的数据只剩分钟均值仍称完整回放。删除按分区进行，保留窗口起点必需的基线及依赖，覆盖元数据同步更新。

容量示例只用于预算，不代表实测：

`1000 台 × 10 条/秒 × 1000 字节 = 10 MB/s ≈ 864 GB/日 ≈ 77.76 TB/90 日`

以上尚未包含事件封装、投影、检查点、索引和副本；压缩率也未测量。你的实际设备数在 1000 台以上，不能把这个例子当容量上限。设备数、平均/峰值频率、报文字节数、留存天数、并发会话和备份副本数须在容量预算确认时落定；原始历史留存、吞吐和成本之间的取舍不得擅自降低数据精度。

预算还必须覆盖下列负载，不能只核算每天落盘量：

- 若一条报文含多设备/点位，直接测实际报文率与编码字节，不能重复按设备数乘算。原始日志、业务变化日志与检查点分别计量，防止每帧全态写放大。
- 热日志容量至少覆盖允许的归档中断及投影追赶窗口，并为实际峰值留余量。积压接近上限时显式告警/背压；到硬上限按交付协议停止确认或登记缺口，不无限吞内存。
- 投影恢复与候选版本追赶的处理速率必须高于持续输入速率；估算追赶时长为“积压量 ÷（有效处理速率 − 新增速率）”。分母非正时无法追上，不能靠反复重试激活解决；旧/候选投影并行的额外 CPU/IO 需要单独预算。
- 每会话回放出口近似为“业务变化字节率 × 倍速”，再叠加并发、快照下载和查询重建成本；不能以单用户 1× 推断多用户 8× 可用。概览可以聚合，完整状态变化不能被网络预算悄悄截掉。
- `SOURCE/DIST`、运行依赖与基线被历史持有的空间，以及备份/恢复时的临时空间，计入同一保留预算。现有资源清理策略不自动代表历史可安全清理。

### 播放、定位与异常反馈

- 进入历史并完成首次恢复后默认暂停，待用户点击播放。暂停冻结历史会话中的业务时钟，包括运动、自驱、TTL、告警求值；服务器实时投影和后台采集继续运行，相机仍可自由查看。
- 拖动开始时暂停推进并记住此前播放状态；拖动过程中只移动目标游标/提示，不连续请求全场重建。松开或完成键盘定位后发起 seek，仅最新 `generation` 可以提交；成功后恢复此前播放/暂停状态。未完成时保留最后有效画面及其时间，失败不把目标时刻标成当前。
- 前后 10 秒与事件导航共用同一 seek 合同，受所选范围、可查询水位和版本约束；不存在可跳事件时禁用相应按钮。到末尾显示已结束并暂停，再次播放可从该范围首个可用时刻开始，不自动循环或切到实时。
- 倍速只调整历史消费与展示节奏，不改变采集频率、不跳过业务事件、不直接放大旧 Babylon 驱动的 delta。处理赶不上时明确缓冲，不能伪装为已按目标倍速播放。
- 拖入缺口时说明不可定位；播放抵达缺口则停在最后有效状态，提供“跳至下一可用时刻”，所选范围内没有后续可用点时提供“调整时间范围”。不得自动跨缺口插值或显示空库存。
- 无数据提示更换范围；加载/恢复失败提供重试并保留有效状态；权限不足不继续显示无权查看的数据。返回实时先显示处理中，完成全态/游标握手后才撤销历史标识；失败仍保持只读，不自动恢复旧 MQTT/Fetch 驱动。
- 范围、滑条、倍速和主要按钮提供可访问名称及可见焦点；键盘快捷键限定在播放控件的焦点范围内，不抢占漫游/相机的按键。普通相机操作不自动结束历史回放；已在执行写记录巡检时，进入历史前提示先结束，不在后台悄悄改变巡检任务。
- 时间轴概览按缩放级别聚合告警/交接等事件；展开细节时再按游标获取，避免一次返回数月事件。原型中的少量事件只作展示示例，不限制实际业务事件种类或历史精度。

### 运行隔离与接续

- 状态机使用 `live → loading → replayPaused/replayPlaying → seeking → returningLive`，并显式表示 `buffering/error`。加载未完成时画面保留最后有效帧，不能让时间标尺先跳到目标而画面仍停在旧时刻。
- 每次 seek 增加 `generation`，取消过期网络请求，失效异步模型生成/资源回调；完成恢复后一次提交新状态，不残留未来货物/告警。
- 不创建两套大 Babylon 场景同时常驻。只读资源缓存可复用，业务状态和消息通道必须会话隔离；实时投影继续在服务器运行。
- 返回实时先解析该场景**当前已生效绑定**及发布版，而不是向历史 `projectionId` 查询“现在”。取得同版“完整当前状态＋游标 C＋续传租约”，在租约内接收 `(C, ...]` 的完整变化；快照下载期间不能丢掉接续所需日志。超过租约/缓冲预算则重取全态，不拼接不连续窗口。不能只重新连接 MQTT 并等待几个最新值，因为旧库存与在途货物不会自动补齐。
- 恢复、跨版本或返回实时失败时保持只读错误/加载状态与最后有效时刻，不提前把模式标为 `live`，不为了掩盖失败启用旧 MQTT/Fetch 驱动。播放过程中遇到配置激活/版本边界，先停止旧投影消费，再解析新版本、资源与基线；历史范围已关闭不等于能继续用旧版本预测当前状态。

开启历史能力的实时/历史入口共用 canonical 游标流，不把没有同一 offset 的浏览器直连 MQTT 混到恢复后的状态里。先实现这种闭环，再接返回实时按钮。

### 非 MQTT 数据与副作用

- 驱动真实业务状态的 Fetch 输入必须由后台同样采集并进入投影；浏览器自己的实时轮询在回放时停止。
- 资产详情、告警面板、弹出大屏传递同一 `TemporalContext`，只能显示对应时刻数据；未接历史的展示明确“该数据无历史支持”，不得混入实时数据。若缺的是货物/库位等必需输入，该版本不能通过完整回溯验收。
- 回放过程允许只读选择、聚焦、相机和历史详情；禁止 MQTT 发布、写操作、自动巡检落库、告警通知和会触发数据编排发送节点的外部联动。权限在数据/动作边界判断，不只把按钮变灰。
- seek 的状态恢复不向外发“新告警/新货物到达”；历史事件导航仅在历史会话内展示。

## 七、接口与代码落点

### 拟新增的服务接口

遵循现有 POST 动作接口风格，前缀拟为 `/api/v1/twin-history`：

| 路径 | 职责 |
|---|---|
| `/capture/config/query` | 编辑器读取绑定项目的配置 revision、来源/存储策略能力及有效配置；管理权限不下放给 Viewer |
| `/capture/config/validate` | 服务器侧预检来源、基线、版本、配额与权限，返回有效值、阻塞项和变更影响，不启动持续采集 |
| `/capture/activate` | 对指定发布版本/候选配置发起幂等应用与启用任务，核验策略与场景绑定 revision，提交成功后才切换有效配置 |
| `/capture/policy/apply` | 对已有成功发布基线显式应用留存/资源策略，不重发场景包，不改变采集启停状态，不重建就绪初态；留存缩短携带独立影响确认 |
| `/capture/pause` | 经授权暂停指定采集关联域，确认受影响场景并关闭完整区间，不删除历史 |
| `/capture/resume` | 对已暂停的有效配置发起幂等恢复，核验 revision；判断可证明补齐还是需要新基线，完成前只标为恢复中，不能沿用暂停前全态宣称连续 |
| `/capture/tasks/cancel` | 取消尚未生效的候选应用任务；已生效任务不能用取消伪装回退，需执行明确的暂停/版本切换 |
| `/capture/status` | 编辑器查询采集任务、候选/有效版本、失败与恢复进度、基线状态和可回放水位 |
| `/coverage` | 查询可回放范围、版本区间、缺口、基线与投影就绪状态 |
| `/sessions/open` | 校验项目/时间范围的读取授权、自身包身份与目标发布版，核验兼容执行产物，固定投影/预算并建立有期限的会话；实时模式不匹配有效绑定时返回等待原因 |
| `/state/at` | 按 `requestId` 幂等准备指定时刻状态，返回准备状态或就绪快照清单、实际游标/时刻/质量；重复同 ID 查询原任务，不重复启动恢复 |
| `/state/chunk` | 在会话授权及快照租约内分块读取同一个不可变状态，校验块摘要；不生成匿名永久下载链接 |
| `/state/cancel` | 取消被新 generation 替代的恢复/预取任务，不能影响实时投影或删除历史 |
| `/changes/query` | 按 `(afterCursor, toCursor]` 取得有界完整业务修订，带 `nextCursor/hasMore/throughTime`；历史窗口与实时接续共用顺序合同 |
| `/events/query` | 查询时间轴关键事件/概览，使用稳定游标而不是深分页 |
| `/sessions/close` | 释放查询/预取、缓存与租约；客户端失联也必须按 TTL 回收 |

连续变化获取需实现可取消、有界的长轮询/批量响应契约，断线按最后成功应用游标续传。不要为本功能启动整套新的消息中间件体系。

当前中台 `AuthService.java` 仍是匿名兼容服务，namespace 不是权限。历史接口必须接可信网关或明确的项目/时间范围读取授权，归档不能直接匿名下载；服务端持有采集凭据，Viewer 只持有短期、只读、限作用域的访问能力。缺少该边界时，不将长期生产历史接口暴露到不可信网络；本任务不顺带重建完整用户角色系统。

## 八、分阶段实施计划

不能把这一范围按“增加时间轴”的小功能估期。先用 **1–2 周**完成第 0 阶段；合同之后立即做一条**包含真实货物流转的最小纵向闭环**，而不是先把全部设备迁移到新架构才发现几何/脚本或初态无法恢复。最小闭环是技术准入，不是将最终交付缩减为演示或设备-only。

以下工作量仍是预算占位，不是已排定交期。以 **2 名前端/状态内核工程师＋2 名 Java/Node 后端工程师＋测试支持，运维与业务人员兼职参与**为参考，原“16–24 周”只能作为早期粗估，缺少最小闭环及真实依赖校准，不能据此承诺生产交付；也不把“2–3 人，6–10 个月”当成可线性换算的结果。完整交期须在阶段 2 后依据单类设备抽取成本、业务脚本清单、查询/归档吞吐和实际人员重排。源基线、部署授权或存储采购未落实是明确阻塞，不能只用增加编码周数解决。

## 九、完成标准与最小验证方式

历史系统的可行性审查仅完成静态代码/契约分析；已确认 UI 的独立原型做过模拟控件和视口检查，但没有接入真实历史服务，不能作为生产回放验证。实施时，确定性、持久确认、千台级有界资源和无副作用不能仅靠 diff 判断，应针对这些具体风险执行最小定向验证，不默认运行全仓测试或新增/改写测试文件。

1. **状态一致：** 用包含生成、跨设备交接、入库、出库、销毁、报警激活/解除的固定输入与明确基线，对比连续推进到 T 和随机 seek 到 T 的业务状态摘要；暂停/倍速不改变同一 T 的离散业务结果，位置误差按阶段 0 约定。同时选取少量关键时点与权威库存/任务/设备记录独立对账，不能只证明同一个新内核重复算出了同样的错误。定向覆盖“单排库存请求挂起时建立检查点，随后旧全量响应与新单排响应先后到达”的恢复：旧响应不覆盖、抑制/保留及货物清算一致，seek 不再次查线上库存。
2. **数据完整性：** 复用协议夹具检查重复、乱序、合法重复心跳、retained、同毫秒消息、设备序号重启及缺口。受控重启核对“持久化后确认”、已提交业务修订及索引，不接受孤立/半写块；暂停/缺失输入后未补齐或重新基线时，不能继续标完整。暂时停止冷归档但仍有热日志预算时，已持久提交的实时流不应等待下一检查点；不把未检测到缺口等同端到端零丢失。
3. **隔离与恢复：** 回放期间实时数据持续到达，历史状态不被覆盖；连续 seek 使旧请求、快照分块和异步资源回调失效。大快照的所有块固定同一游标，缺块不安装；变化分页不拆开货物原子交接。返回实时从当前生效版本全态接续；失效游标、版本切换和租约过期重新握手，不重复/遗漏货物，不自动回落旧业务驱动。
4. **真实 Viewer 与已确认 UI：** 实施后对照第六节归档截图和交互合同，使用真实浏览器操作范围选择、播放/暂停、倍速、拖动/键盘定位、前后 10 秒、事件跳转、收起及返回实时，检查控制台和网络；定位未完成时当前时刻不提前变化，快速拖动仅最新任务提交，末尾/缺口不自动跳回实时，暂停不锁相机，窄屏与现有浮窗不互相遮挡。核对空区间、加载失败、历史详情，并确认没有 MQTT 发布、业务写请求、流程调用或新的巡检记录等副作用。跨版本至少确认一次兼容执行产物选择：先进入只读历史模式，再加载锁定资源/状态，不先执行旧 DIST 的实时启动链路。保留必要截图证据，不把原型中的示意数据验收当作真实数据验收。
5. **规模与保留：** 用阶段 0 的设备/频率/包长和约定会话数执行有界采集及查询样本，核对吞吐、落盘、积压、内存/窗口上限和 seek 延迟；用受控短保留分区验证清理后仍可从窗口边界恢复，以及资源版本不会被误删。不得据此声称实际运行了数月。
6. **权限与文档：** 非授权项目/时间范围被拒绝，发布包不含服务端凭据；部署、留存、备份恢复、缺口含义及操作方式与实际交付一致。
7. **编辑器配置闭环：** 实施配置 UI 后，用真实编辑器验证配置应用、取消、保存与重新打开，未绑定/离线草稿和服务端预检提示；确认 MQTT/Fetch 修改会使旧预检失效。再沿一次“发布 → 显式启用 → 关闭编辑器 → Viewer 回放”链路检查服务端状态：发布未提交/应用失败时旧有效策略不变；同一幂等键重试返回原结果，不同命令竞争同一预期 revision 仅一个生效；纯留存策略可针对已有发布版本应用而不重打包、不改变启停状态。新包已部署但未激活/激活失败，以及普通发布回滚时，Viewer 必须先核验包身份与有效绑定；不匹配显示等待而非消费旧投影。定向核对留存缩短影响确认、SOURCE/DIST 无凭据及 Viewer 无采集管理权限；沿用已有场景保存/发布夹具，只执行与这些新边界直接相关的检查。

只有“编辑器配置/发布闭环＋完整初始状态＋持续证据＋同版本业务内核＋可恢复检查点＋只读 Viewer 闭环”全部成立，才将该场景版本标为完整时光回溯可用。
