# 发布前恢复缺失模型

点击“发布到数据中台”后，编辑器先检查场景模型、模型生成器、报警模型、漫游人物和点击事件设备类型的模型引用，再保存场景和生成 SOURCE、Viewer DIST 包。

- 点击设备类型与场景已有模型属于同一个中台资源且包内模型路径一致时，重新关联到现有场景快照，保留实例位置、资产编号、参数、遥测配置和事件。
- 场景实例的模型或脚本文件丢失时，按中台稳定模型 ID 定向重新获取完整模型包，并更新已有实例的资源引用。模型文件、元数据和脚本沿用现有下载及包校验。
- 点击设备类型没有任何场景模型或可生成设备的目标时，重新获取该模型包，在场景原点加入一个真实模型，并将点击槽位关联到它。同一类型只补入一次；重复发布不会增加副本。报警筛选模板和漫游人物不算可点击设备实例。
- 恢复操作作为一次可撤销场景修改写入编辑器。后续保存和 SOURCE、DIST 打包使用修复后的同一份场景快照，槽位和事件列表不会因缺失引用被静默清空。

原始槽位没有保存已删除实例的位置和业务资产编号。新增实例采用模型包默认配置和新资产编号，并放在场景原点；需要按实际业务调整布局与资产编号。对于启用了烘焙阴影的场景，模型补入或资源更新使原烘焙失效时，恢复结果仍保留在编辑器中，更新阴影后再次发布。

模型不存在、详情返回错误 ID、资源校验失败、无法识别中台模型 ID，或同一资源涉及多个不同包内模型且无法确定变体时，停止发布并显示原因。不会仅按显示名称猜测模型，也不会清空槽位后继续发布。下载期间可以取消；同时编辑或切换场景后，旧恢复结果不能覆盖新场景。

恢复只定向刷新需要的普通或组合模型，共享资源库中的其它模型保持原样，工程内已有可用快照保持不变。后台模型同步与恢复事务串行提交，避免互相覆盖索引。

验证命令：

```powershell
node --experimental-strip-types --test --test-concurrency=1 tests/digitalTwin/clickEventModelRecovery.test.ts tests/editor/publishModelRecovery.test.ts tests/dataPlatform/modelIncrementalSync.test.ts
npm run test:publish-model-recovery
```

集成测试使用本地模拟数据中台和真实 GLB 文件，覆盖定向 HTTP 下载、编辑场景补入模型、SOURCE/DIST ZIP、Viewer 重新加载，以及模型/货格点击、高亮、聚焦、资产编号与大屏事件。测试不向业务数据中台创建发布记录；已有线上发布包需要重新发布才能使用修复结果。
