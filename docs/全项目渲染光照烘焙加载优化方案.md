### 0.2 不可变契约（主路线）

沿用 `project-optimization-plan.md` 第一章：保持 WebGL2、MSAA/FXAA、stencil、GlowLayer 与选中描边、分辨率/DPR、完整几何与材质；外置 `.model.ts`、`dataDriven.motion` 及各设备驱动算法、MQTT 消费顺序和频率不变；`.scene.json` v1–6、`sceneSettings.lighting` v2、`appearance` v1、SOURCE/DIST 安全边界兼容。

### 0.3 档位定义

- **档位 A（主路线）**：画面像素、几何、资源身份不变，或只修正已有错误。默认可启用。
- **档位 B（可选有损）**：会改变画面（LOD、有损纹理压缩、自适应分辨率、空闲降帧、遮挡剔除、小物体不投影等）。**默认关闭**，作为场景或发布配置的显式选项，单独做同视角截图与业务验收，结果不得计入档位 A 的收益。
- **增强档**：在强显卡上提高画质（更高阴影分辨率、更多级联等）。默认值保持现状，不因硬件弱而自动降级。

### 0.4 硬件分级

目标硬件不固定型号，但一定存在比核显更强的显卡。方案按能力分级，而不是按型号：

| 级别 | 判定依据（实施时由 R1 实测校准） | 用途 |
| --- | --- | --- |
| T0 基线 | 集成显卡或实测 GPU 预算紧张（如 Intel UHD630 级） | 默认画质、所有 CPU 优化的验收下限 |
| T1 主流独显 | 独显 renderer、`maxTextureSize ≥ 16384`、基准帧时间达标 | 可选增强档 |
| T2 高端独显 | T1 且基准渲染余量充足 | 增强档上限 |

结论：当前工厂与展会两个实测样本都显示 **CPU 主线程是首要瓶颈**（展会 RTX 5060 下 GPU 渲染约 11 ms，但长任务 38 s/60 s）。因此 CPU 侧优化对所有级别都有效，优先级最高；GPU 侧优化主要惠及 T0。

### 0.5 标记约定

- 优先级：**P0** 低风险速赢；**P1** 主要收益项；**P2** 需设计/有条件；**P3** 研究项。
- 每项写明：位置、证据、方案、可行性依据、风险与回退、验收。
- “需核对 API”：本工作区无 `node_modules`，涉及 Babylon 9.12 API 的项目必须先在已安装依赖中确认签名后再实施。

## 2. 光照（运行时分类、GI 与灯光）

### L1（P0）UI 分类轮询改为按需

- **位置**：`src/editor/panels/scene-view/useSceneLightingPreview.ts:184-197`。
- **证据**：定时器每 400 ms 调用 `runtime.getLightingClassification()`，与 `lightingManagerOpen` 无关；分类脏时会同步触发一次全量收集。工厂 95 次全量收集中 37 次由此触发。
- **方案**：
  1. 定时器只在 `lightingManagerOpen` 为真，或当前选中对象的 Inspector 正在显示“烘焙与阴影”摘要时运行；
  2. `getLightingBakeRuntimeError` / `getLightingRuntimeDiagnostic` 这类只读状态保留轮询，但改用不触发收集的只读查询（若当前实现会触发收集，需拆出 `peek` 版本）；
  3. Inspector 摘要改为只查询选中实体：新增按实体 ID 返回缓存条目的接口，缓存过期时显示“待刷新”，不强制全量收集。
- **可行性**：纯 UI 订阅条件变更，不改运行时语义；管理器打开时行为与现在一致。
- **风险/回退**：管理器打开瞬间分类数据稍晚一帧——打开时立即触发一次刷新。回退方法是恢复原依赖数组。
- **验收**：管理器关闭时 60 s 内由 UI 触发的 `getSources` 为 0（复用 `lightingInvalidation.ts` 原因计数）；`npm run test:lighting-manager`、`npm run test:lighting-optimization` 通过。

### L2（P0/P1）Mesh add/remove 按净变化抵消

- **位置**：`ModelAssetRuntimeController.suspendModelArrayHost / restoreModelArrayHostMeshes`（注释见 364-368 行：为减少每帧遍历把宿主叶网格移出 `scene.meshes`）；事件入口 `SceneTriangleAndReadinessController.ts`；`lightingInvalidation.ts`、`SceneLightingRuntime.notifyMeshLifecycleChange`。
- **证据**：同一宿主在遥测/脚本更新时先 restore 再 suspend，产生成对的 added/removed；上一轮只合并了重复标记，消费时仍做全量收集。
- **方案**：
  1. 失效入口为 `scene-mesh-added/removed` 原因维护“待定成员变化集合” `Map<AbstractMesh, 'added'|'removed'>`，同一网格的相反事件互相抵消；
  2. 记录上次成功收集时每个相关网格是否在 `scene.meshes` 中（只记录宿主挂起集合涉及的网格，用 `WeakMap` 存放）；
  3. 消费时，若待定原因**只有**成员变化，且所有网格的当前成员状态都与上次收集时相同，则跳过全量收集；
  4. 只要同时存在 `model-meshes-refresh-unknown`、classification 或 structure 原因，就照常全量收集。
- **可行性**：挂起宿主的网格由阵列批次代表，挂起/恢复往返不改变分类输入；脚本可能产生的实质变化另由 `refreshModelMeshes` 的 unknown 原因覆盖，本项不削弱该路径。
- **进阶（P2）**：评估 suspend 改为“保留在 `scene.meshes` 但 `setEnabled(false)` 并跳过评估”。需要先量化 Babylon 对禁用网格的遍历成本是否抵消收益，否则保留原 remove/add。
- **风险/回退**：网格在往返期间被替换了几何或材质——这种情况会通过 `onGeometryUpdated`/材质事件走其他原因，不会只剩成员变化。回退方法是关闭净变化判断。
- **验收**：工厂回放 60 s 内由成员变化触发的全量收集次数下降，且 `refreshModelMeshes` 触发次数不变；GI/阴影角色与原版逐帧一致（复用 `sceneMeshLightingInvalidation.test.ts`、`sceneLightingRuntime.test.mjs`）。

### L3（P1）分类按消费者需要收集

- **位置**：`SceneLightingRuntime.tick` / `refreshBindingsForSources`（723-759 行）、`updateShadowRoles`（890-913 行）。
- **证据**：分类结果的消费者只有三个：GI 绑定、阴影角色（`setHybridMeshRoles` / `LightingShadowInstanceRuntime`）和管理器 UI。
- **方案**：当 `lighting.shadows.enabled === false`、没有已应用的 GI `result`、管理器未打开、也没有烘焙/预检任务时，`tick` 只保留 dirty 标记、不收集。任一消费者出现时立即补一次全量收集。
- **可行性**：此时分类结果无人读取；消费者出现时补收集，行为与“刚打开场景”一致。
- **风险**：其他模块隐式依赖 `lightingRuntime` 的副作用（如 `shadowInstances`）——实施前用调用图核对 `getLightingClassification` 与 `onBindingsChanged` 的所有使用点。
- **验收**：无阴影、无 GI 的场景中，分类收集次数为 0；开启阴影后一帧内角色正确。

### L4（P1）按模型增量缓存分类

- **位置**：`EnvironmentAndSkyboxController.initializeLightingRuntime → getSources → collectLightingRuntimeSources`（`lightingClassificationRuntime.ts`）。
- **证据**：每次收集都对全部模型、变体、生成输出、薄实例批次和环境重新遍历节点、解析策略并生成键。工厂单次 300–535 ms。
- **方案**：
  1. 把收集拆成“每个来源单元一次”：普通模型、阵列变体、生成输出、批次、环境各为一个单元；
  2. 每个单元缓存 `{ revision, sources[] }`。revision 由以下各项组成：模型 `loadToken`、网格集合身份版本、几何/材质事件计数、策略规则版本（`sceneSettings.lighting.policy` 内容哈希）、实体 `components.lighting` 版本、运动目标版本（`getLightingMotionNodes` 结果引用）；
  3. 失效事件能定位到实体时（Mesh metadata 中的 `entityId`、`refreshModelMeshes(model)`），只标记该单元；不能定位或原因为 unknown 时，标记全部单元；
  4. 合并阶段按原顺序拼接各单元结果，重新做全局键唯一性检查（保留 `SceneLightingRuntime.ts:474-476` 的重复键报错）。
- **关键约束**：
  - 脚本可能修改其他模型。因此“脚本执行”类失效默认标记**脚本宿主自身加上所有子孙**；如果脚本运行时上下文能报告其写入了其他实体，就扩大范围；无法证明时整场失效。
  - 策略规则、场景默认值变化必须让全部单元失效。
- **可行性**：收集函数本质是“按来源单元映射后拼接”，天然可分解；增量与全量结果可以逐条对比做影子校验。
- **实施步骤**：先实现“影子模式”——增量结果与全量结果同时计算，比较 key/entry 全字段，不一致就上报并使用全量结果。在真实工厂运行 30 分钟零差异后，再切换为增量为主、周期性（如每 10 s 或每 N 次）全量对账。
- **验收**：影子比较零差异；工厂回放单次收集中位耗时下降，相关长任务累计下降；`test:lighting-bake`、`test:lighting-manager`、`test:optimization-p2` 通过。

### L5（P1）分类合并窗口与分片执行

- **方案**：
  1. 收集频率上限：连续脏信号在 N ms（建议 250 ms，实施时以实测定）内只消费一次，管理器打开或烘焙前强制立即消费；
  2. 结合 L4，把各单元的重新收集分散到多帧执行，每帧预算约 4 ms（复用 `scenePreparationFrameBudget` 的思路）；全部完成后再原子替换 `this.sources`，期间若有新的失效则重新开始。
- **安全性依据**：`HybridShadowMeshState.isStatic(mesh)` 对未登记网格返回 false，未分类的新网格默认按动态处理——不会被写入静态阴影缓存，最坏情况是多渲染一帧动态阴影。GI 生效时，静态源变化本来就会触发整体失效，不依赖分类时效。
- **风险**：新出现的网格在合并窗口内的 cast/receive 可能沿用默认值。需在验收中检查货物生成首帧的阴影。
- **验收**：长任务中“单次 > 50 ms 的分类任务”数量明显下降；阴影角色在窗口结束后一致；`smoke:hybrid-shadows` 通过。

### L6（P1）GI 每帧静态校验改为事件驱动加分片

- **位置**：`SceneLightingRuntime.ts:779-822`（tick）、`lightingRuntimeCapture.ts:115-124`（`lightingMaterialFingerprint`）、`captureLightingEnvironment`。
- **证据**：GI 生效后每帧对 `state.staticWatch` 全量执行：材质指纹（数组 + `getActiveTextures` + 内容哈希）、`computeWorldMatrix(true)`（绕过冻结矩阵）、可见性判断；每帧还对整个灯光环境做一次内容哈希。
- **方案**：
  1. **矩阵**：改用 `mesh.onAfterWorldMatrixUpdateObservable` 记脏，配合矩阵 `updateFlag` 数值比较；不再每帧强制计算。冻结的网格直接跳过。
  2. **材质**：对静态源用到的材质和纹理订阅 `Material.onBindObservable` 以外的可靠失效信号（`markAsDirty` 包装 / `Texture.onLoadObservable` / 材质替换的 `onMaterialChangedObservable`），用“版本号 + 采样复核”替代每帧指纹。
  3. **灯光签名**：订阅灯光属性变化（`Light` 的 position/direction/intensity/diffuse setter 无统一事件时，复用 `SceneLightRigRuntime` 与实体灯同步入口发出的版本号）；`scene.environmentTexture` 和 `environmentIntensity` 变化在设置入口记版本。
  4. **兜底**：对无法覆盖的直接写入，每帧轮询少量静态源（预算 0.5 ms），保证全集在约 1 s 内被完整校验一遍。
- **语义影响**：未通过事件捕获的变化会最多延迟约 1 s 才判定 GI 过期。过期只会让画面恢复实时基线，不会产生错误结果。该延迟须在文档和验收中明确记录。
- **验收**：GI 生效、无变化时，tick 自耗时降到 1 ms 以内；已有 GI 失效测试（几何、姿态、材质、灯光）全部通过，包括“同帧修改”用例；`test:lighting-bake`、`smoke:baked-lighting-material` 通过。

### L7（P2）探针采样去分配

- **位置**：`lightingProbes.ts:24-50`、`SceneLightingRuntime.updateDynamicBindings`（824-866 行）。
- **证据**：每次采样生成 27 个字符串单元键，使用 `map`/`hypot(...spread)`、`Array(18).fill`、`result.map`；遮挡查询对象在每个采样帧重建（`staticWatch.filter(...).map(...)`）。
- **方案**：单元键改为整数哈希（`(x*73856093) ^ (y*19349663) ^ (z*83492791)` 加冲突链）；预分配候选数组和 18 元结果缓冲；`LightingProbeOcclusionQuery` 在 state 生命周期内只建一次，静态集合变化（本来就会让 GI 失效）时重建；采样位置变化阈值保持 1 cm 不变。
- **验收**：插值结果与原实现逐位一致（同输入同排序）；运动设备较多时 `updateDynamicBindings` 自耗时下降。

### L8（P1）点光/聚光按范围裁剪受影响网格

- **位置**：`SceneMeshPresentationController.ts:210-234`（实体灯创建）、`SceneShadowRuntime`。
- **证据**：Babylon 的 `light.canAffectMesh` 只检查 include/exclude 列表和层掩码，不检查 `range`；材质 `maxSimultaneousLights` 默认为 4。灯多的场景中，每个网格按场景顺序取前 4 盏灯，可能漏掉附近真正照到它的灯，同时让远处灯的着色成本落在每个片元上。
- **方案**：对 `range` 有限的点光和聚光，按“网格世界包围球与灯光范围球（聚光再加锥体测试）相交”维护每盏灯的 `includedOnlyMeshes`。静态网格只在灯光或网格变换时重算；动态网格按帧或按移动阈值重算。方向光、半球光不处理。
- **画质说明**：范围外的贡献在衰减模型下本来为零，裁剪不改变像素；同时修正“最多 4 盏灯选错”的问题，属于正确性改进，因此归档位 A。若某种衰减模型（如 physical）在范围外仍有非零贡献，则该衰减模型的灯不裁剪——实施前需按 9.12 着色器核对。
- **风险**：频繁变化 `includedOnlyMeshes` 会触发材质重编译，因此只在集合变化时写入，并做批量处理。
- **验收**：多灯测试场景同视角截图像素差在原阈值内；着色器变体数和材质重编译次数不上升；`test:light-editor`、`smoke:lighting-types` 通过。

### L9（P1）合并 GlowLayer

- **位置**：`effects/TargetModelEffects.ts:420-421`、`589`。
- **证据**：配置了 `glowRadius` 或 `glowIntensity` 的每个效果各创建一个 `GlowLayer`。每个 GlowLayer 都是一次额外的发光渲染加全屏模糊；报警效果多时 GPU 成本线性增长。
- **方案**：GlowLayer 按模糊半径（`blurKernelSize`）分组共享；强度差异通过 `customEmissiveColorSelector` 按网格缩放发光颜色实现，不再依赖层的 `intensity`。最终层数等于不同半径的数量（建议把半径量化到配置中实际出现的值，不做强制取整）。
- **画质**：同半径下逐网格强度经由发光颜色缩放，与层强度等价（层强度本质是合成时的乘数，需按 9.12 核对 `intensity` 的作用位置，确保与颜色缩放线性等价后才合并）。
- **验收**：多报警场景截图对比在原阈值内，GlowLayer 数量等于不同半径数；`test:contracts:effects` 通过。

### L10（P2）泛光开启时恢复 MSAA

- **位置**：`SceneAppearanceRuntime.ts:31-40`。
- **证据**：启用泛光后场景渲染到后处理 RT，引擎画布的 MSAA 不再作用于场景，当前用 FXAA 代替，边缘质量与关闭泛光时不一致。
- **方案**：WebGL2 下设置 `pipeline.samples = 4`（需核对 API），并在 MSAA 生效时关闭 FXAA；T0 保持当前 FXAA，T1/T2 启用 MSAA（增强档）。
- **验收**：开关泛光前后边缘锯齿一致；GPU 帧时间变化记录在案。

## 3. 阴影

### S1（P1）混合阴影静态签名改为数值比较

- **位置**：`HybridShadowCache.ts:86-138`（`HybridShadowMeshState.refresh`）。
- **证据**：每帧对每个静态投射体构造一个由世界矩阵 16 个分量、几何版本、顶点/索引数和全部 subMesh 材质字段拼成的字符串，再与上次字符串比较。静态投射体达到数千时，这是持续的字符串分配和 GC 压力。
- **方案**：
  1. 每个网格保存一份 `Float64Array(16)` 矩阵快照，先比较矩阵的 `updateFlag`，变化时再逐分量比较；
  2. 材质部分改为结构化的数值/引用元组缓存：`uniqueId`、alpha、裁剪模式等逐字段比较；`DynamicTexture` 仍按帧失效（保留 113-114 行语义）；
  3. 先比较几何版本和可见性等廉价字段，任一变化即判定改变，不必继续比较其余字段；
  4. `computeWorldMatrix(geometryChanged || !mesh.isSynchronized())` 保持不变（同一 renderId 的修正逻辑需要它）。
- **验收**：判定结果与原字符串方案逐帧一致（新增等价性测试，覆盖矩阵、透明裁剪、动态纹理、几何更新）；静态缓存命中率不变；`test:optimization-p2` 中的 `hybridShadows.test.ts`、`smoke:hybrid-shadows` 通过。

### S2（P1）质量档使用 hybrid 静态缓存

- **位置**：`SceneShadowRuntime.ts:51-75`、`690-740`。
- **证据**：`quality` 档使用 3 级 2048 级联阴影且每帧刷新（`cached:false`）。厂房场景绝大多数投射体是静态的，hybrid 模式已经具备“静态深度缓存加动态叠加”的能力。
- **方案**：在管理器的阴影质量说明中，把“hybrid + 静态缓存”标为大场景推荐配置；新建场景默认值保持不变（变更默认值需另行确认）。补充成本面板：按“每帧阴影绘制数 / 缓存命中”显示收益（已有 `getHybridLightingMetrics`）。
- **验收**：工厂场景开启后阴影像素对比在 `smoke:hybrid-shadows` 原阈值内，阴影 pass 每帧绘制数下降。

### S3（增强档）按硬件能力提高阴影分辨率

- **验收**：T1/T2 机器上阴影边缘清晰度提升，帧时间增加在预算内；T0 行为不变。

### S4（档位 B，默认关闭）阴影降成本

## 4. 烘焙（Blender/Cycles 离线管线）

当前链路：Editor 捕获静态输入（二进制几何附件 + JSON 清单）→ 独立 Blender factory-startup 进程执行 `cycles_bake.py` → 输出 RGBM PNG 图集、逐网格几何 JSON、`probes.json` → 校验后写入 `Assets/LightingBakes/<任务>/`。

### B1（P0）用 numpy 向量化像素处理

- **位置**：`cycles_bake.py:886-898`（间接光与环境两遍结果合并）、`905-923`（`save_rgbm`）、`1056-1064`（探针像素读取）。
- **证据**：2048² 图集有 1,677 万个 float 分量，`save_rgbm` 用 Python 生成器求最大值后再逐像素编码，合并阶段也逐像素循环。单张图集的 Python 循环就是秒级到数十秒级；工厂 42 张图集时累计为分钟级。
- **方案**：Blender 自带 numpy。`image.pixels.foreach_get(np_array)` 读入 `float32` 数组后：合并用 `np.maximum(a + b, 0)`；RGBM 编码用向量化的 `max/ceil/divide`；探针用切片求均值；写回用 `foreach_set`。
- **等价性**：要求与原 Python 实现逐像素一致。浮点运算顺序可能导致末位差异，验收以“编码后 8 位 PNG 字节一致，或差异不超过 1 LSB 且有明确统计”为准，预先固定判定阈值。
- **验收**：`npm run test:lighting-bake:cycles` 全部通过；同输入新旧脚本产物逐像素比较；记录每张图集的耗时。

### B2（P0/P1）减少 `bpy.ops.object.bake` 调用次数

- **证据**：每次 bake 调用都要重新同步场景并构建 BVH。当前每张图集 2 次调用；探针每 64 个 2 次调用（128² 图像，`1024-1068` 行），4096 个探针需要 128 次调用。
- **方案**：
  1. **探针（P0）**：把探针图像从 128² 扩大到 1024²。瓦片布局不变（每面 4×4 像素，四周各留 1 像素，即每个瓦片 6×6 像素），每行 170 个瓦片，共 28,900 个面，每批约可容纳 4,816 个探针。4096 个探针只需 1 批，即 2 次调用，而不是 128 次。float 缓冲约 16 MiB。采样像素位置与面法线顺序不变。批次大小保留为可配置常量，以便按显存调整。
  2. **图集（P1）**：在内存预算内（如 512 MiB float 缓冲，即 2048² 时约 8 张）把多个图集页放进同一次 bake。每页的对象使用各自的材质副本，指向该页的目标图像，这样一次调用就为多页同时写出结果。由于材质可能被多个页面共享，需要按页复制材质并在完成后清理。
- **可行性**：Cycles bake 原生支持“多个选中对象各自的活动图像节点”；探针改变的只是 UV 布局常量。
- **风险**：大批次的 GPU 显存峰值更高。GPU 模式下批次大小按设备显存自适应，出现显存错误时沿用已有的 `is_gpu_memory_error` 回退路径并缩小批次重试。
- **验收**：探针结果与原批次逐值比较（Cycles 采样噪声的随机种子不同，需用固定 `seed` 或统计阈值判断）；烘焙总耗时下降；`test:lighting-bake:cycles` 通过。

### B3（P1）执行设备默认改为“自动”

- **位置**：`cycles_bake.py:1094-1131` 已实现 OptiX/CUDA/HIP/oneAPI/Metal 探测和 CPU 回退。
- **方案**：在管理器中把默认值从 CPU 改为“自动”。检测到 GPU 时使用 GPU，失败时回退 CPU 并记录原因（逻辑已有）。这属于产品默认值变更，需确认。
- **验收**：有独显的机器上，同一工程烘焙耗时对比；回退原因写入任务历史。

### B4（P2）没有环境照明时跳过第二遍

- **位置**：`cycles_bake.py:888-898`（隐藏灯光后的 direct 一遍用于获取环境直射）。
- **方案**：当世界节点的环境强度为 0，或背景颜色全黑且没有 HDR 时，跳过第二遍，环境直射项按 0 处理。
- **验收**：有环境和无环境的两种夹具，产物与原流程一致。

### B5（P3 研究）降噪

- **背景**：Cycles bake 本身不降噪（`use_denoising` 只作用于渲染）。降噪可以让同等质量所需的采样数降低数倍。
- **可行方向**：在烘焙结束后的独立步骤中，用合成器的 `Denoise` 节点（OIDN）处理浮点图集：Image → Denoise(HDR) → Composite，配合空场景的 1 采样渲染触发合成。降噪后需要按 UV 岛掩码重新扩边，防止跨岛渗色。
- **门槛**：同等采样下降噪结果对比高采样参考图，误差统计和人工视觉验收都通过后，才把“标准质量”从 64 采样调低；否则保持现状。

### B6（P0/P1）GI 几何导出焊接为有索引格式

- **位置**：`cycles_bake.py:926-959`（`indices.append(len(indices))`，按角点展开）；运行时 `SceneLightingRuntime.ts:561-566` 直接使用 positions/indices；校验函数 `electron/shared/sceneLightingBakeArtifacts.ts` 的 `validateLightingGeometry`。
- **证据**：每个三角形角点都是独立顶点，顶点数等于 3 倍三角面数。文件体积、解析时间、GPU 显存和顶点缓存命中都受影响。
- **方案**：导出时按完整属性元组焊接——(position, normal, uv, uv2, color, tangent, bakeUv) 完全相同的角点合并为一个顶点（用字典去重，键为属性值的精确字节）。原三角形的角点顺序（含翻转修正）保持不变。几何资源格式升到 `version: 2`。运行时和校验函数同时接受 v1 和 v2，结果清单记录格式版本。
- **等价性**：只合并属性完全相同的角点，渲染结果与 v1 逐像素一致（光栅化等价）。UV 岛边界上的角点 bakeUv 不同，不会被合并，因此原注释中“UV 岛边界不会覆盖相邻面”的约束依然成立。
- **预期**：典型网格顶点数下降约 3–6 倍（以实测为准），JSON 体积和解析时间同比下降。
- **验收**：`test:lighting-bake`、`test:lighting-bake:cycles` 通过；新增 v1/v2 渲染像素对比；发布 SOURCE/DIST 的资产校验通过。

### B7（P1）几何资源改为二进制

- **方案**：新增 `.bin` 资源格式：小型 JSON 头（版本、属性布局、偏移、数量）加连续的 `Float32Array` / `Uint32Array` 数据（输入侧已使用 Float64 附件；运行时 VertexData 本来就是 Float32）。运行时用 `ArrayBuffer` 切片直接构造 TypedArray，不经过 JSON.parse。旧 JSON 资源继续可读。
- **兼容**：资源清单的 `kind: 'geometry'` 增加 `encoding: 'json' | 'binary-v1'` 字段，缺省按 JSON 处理；SOURCE/DIST 的复制、SHA 校验和 URL 重写逻辑按文件处理，不需要改动。
- **验收**：大场景 GI 资源加载耗时和峰值内存对比；`test:lighting-unified`、`smoke:lighting-unified` 通过。

### B8（P2）RGBM 编码精度

- **位置**：`cycles_bake.py:905-923`；解码在 `BakedLightingMaterialPlugin.ts:58-62`。
- **证据**：动态范围取整张图集的最大值。单个高亮像素（如灯具附近）会抬高整张图集的范围，暗部的 8 位精度随之下降，容易出现色带。
- **方案**：新增 `encoding: 'rgbm-gamma'`：编码前对 `rgb / range` 先开平方（gamma 2），解码时再平方，暗部精度明显提高。旧的 `rgbm` 继续支持（着色器按 define 分支）。不采用截断最大值的做法，以遵守“不夹断数值”的约束。
- **验收**：暗部色带对比（固定曝光截图）；`smoke:baked-lighting-material` 通过。

### B9（P2，默认关闭）光照图 mip

- **位置**：`lightingRuntimeResources.ts:50`（`noMipmap = true`，双线性采样）。
- **证据**：远距离观察时没有 mip 会产生闪烁，大图集的纹理缓存命中也较差。
- **方案**：可选生成 mip，同时把 bake 扩边（`bake.margin = 3`）提高到不少于 2^k 像素，并限制最大 mip 级数，防止相邻 UV 岛混色。RGBM 做线性过滤存在近似误差，需要视觉验收。
- **归类**：会改变远景外观，归入**档位 B**，默认关闭。

### B10（P2 研究）合并静态 GI 代理以减少 Draw Call

- **证据**：GI 生效时，每个静态表面都有一个独立代理 Mesh（`prepareState` 551-575 行），薄实例批次也被拆成逐实例 Mesh。
- **前提**：静态源的姿态、显隐、几何、材质任一变化都会让 GI 整体失效（`tick` 805-811 行），所以静态代理在 GI 生效期间是真正不变的。
- **方案**：
  1. 按（工作材质, 图集纹理, 渲染组, receiveShadows, layerMask）分组，把代理顶点数据拼接成一个世界空间网格，每组一个 subMesh；
  2. 维护“三角面区间 → 光照源键/实体 ID”的有序表，拾取时用 `pickInfo.faceId` 二分查找映射回实体；
  3. 选中描边仍使用原代理或原源网格单独渲染：只在选中时临时创建或启用该实体的代理，供描边层使用。
- **门槛**：拾取、框选、描边、点击事件、Viewer 交互全部通过，Draw Call 下降且帧时间改善，才进入默认路径；否则保持逐代理方案。

### B11（P3 研究）薄实例共享光照图 UV 加实例 scaleOffset

- **思路**：同一源几何只做一次 UV 展开；每个实例在图集中占据一个矩形，用 `thinInstanceRegisterAttribute('lightmapScaleOffset', 4)` 传入缩放和偏移（需核对 API）；同一批次按图集页拆分。这样 GI 生效时仍能保留薄实例合批。
- **约束**：非均匀缩放的实例无法共享同一 UV 布局（纹理密度不同），需回退为独立代理；烘焙端 UV 打包需要改为“按源几何复用岛 + 实例矩形”的方式。

### B12（P3 研究）增量烘焙

- 只重新烘焙输入签名发生变化的图集页。难点在于间接光的全局耦合（任何静态几何变化都会影响其他表面的反弹）。仅在“只增删远离其他表面的孤立对象”等可证明的情况下考虑，默认仍然全量烘焙。

- **验收**：A 档产物语义校验通过、加载耗时和文件体积下降；B 档逐模型截图验收。

### LD3（P1，需决策）天空盒发布期预过滤

- **位置**：`SceneSkyboxRuntime.ts:263-300`（下载、Worker 解码、构建立方体纹理、`HDRFiltering.prefilter`）。
- **方案**：
  1. 发布（DIST）时在 Editor 渲染进程中用 `EnvironmentTextureTools.CreateEnvTextureAsync` 生成预过滤的 `.env`（RGBD 编码，通常为 MB 级，需核对 API）。IBL 光照直接加载 `.env`，Viewer 不再在运行时预过滤。
  2. 背景显示仍需要原始全景图的清晰度。可选做法：背景在首帧之后渐进加载原始 HDR/EXR，加载完成前显示 `.env` 的最高 mip。
- **需决策**：当前的就绪契约要求天空盒在首帧前就绪。渐进加载背景需要修改契约（区分“照明就绪”和“背景就绪”）；不改契约时只能获得“免去运行时预过滤”这一部分收益。
- **验收**：Viewer 首帧时间、下载字节对比；IBL 光照像素与运行时预过滤结果一致（同分辨率下对比，阈值预先固定）。

### LD4（P3 研究）作者声明式脚本几何缓存

- **背景**：现有方案认定“通用跨会话几何复用需要纯度证明”，无法自动推断。
- **方案**：在模型包元数据中增加作者声明，例如 `parameterGeometry: { deterministic: true, dependsOn: ['parameterValues'] }`。只有声明了的包，才按（GLB SHA + 脚本 SHA + 规范化参数签名 + 编译器版本）缓存脚本生成的几何；`constructor` / `onStart` 仍完整执行（保留生命周期契约），但几何构建 API 命中缓存时直接返回。
- **门槛**：需要脚本运行时提供可拦截的几何构建入口。如果脚本直接操作 VertexData，则无法安全拦截，此项暂缓。

### LD5（P1）货物对象池

- **位置**：`modelGeneratorRuntime.ts`、`scene-runtime/GeneratedModelOutputController.ts`。
- **证据**：展会场景中货物持续生成，`modelClone` 持续增长，每秒出现 2–6 个长任务。预取只解决了解码，没有解决克隆、建树和绑定的成本。
- **方案**：仅针对**共享实例类**货物（`resolveModelAssetSharedInstancingPolicy` 返回 `shared-instance`，即没有脚本、参数和动画的普通模型）：
  1. 回收时不释放，改为 `setEnabled(false)` 并重置变换、父节点、材质覆盖和 metadata，然后放回池中；
  2. 生成时从池中取出，赋予新的逻辑 ID 并重新绑定交接关系；
  3. 池容量有上限（例如按生成器配置的最大在场数量），超出时照常释放。
- **约束**：独占容器类货物（有脚本或参数）不进池；点击身份、交接、父子归属、故障材质在复用前必须完全重置，并有专门回归测试。
- **验收**：连续生成和交接期间克隆次数接近 0，长任务下降；货物身份、交接轨迹与原版逐时刻一致（`test:generated-cargo-preload` 及交接相关测试）。

### LD6（P1）准备阶段预编译着色器

- **证据**：项目中没有使用 `material.forceCompilationAsync` 或 `ShadowGenerator.forceCompilationAsync`（需核对 API）。货物首次出现、报警效果首次触发、GI 材质首次绑定时，都会在运行中途编译着色器。
- **方案**：在准备蒙版期间，对以下对象预编译：货物模板材质（结合已有预取）、效果克隆材质的常用变体、阴影生成器的深度材质、GI 插件材质。所有预编译都是有界并发，计入准备进度。
- **验收**：首次生成或首次报警时的帧时间尖峰下降；准备耗时的增量单独记录（把成本挪到打开阶段时不能宣称成本消失）。

### LD7（P1）DIST 预压缩

- **方案**：发布时为 JS/CSS/JSON/WASM/场景 JSON/GI 几何 JSON 生成 `.br` 和 `.gz` 文件，Nginx 模板启用 `gzip_static on;`（以及安装了 brotli 模块时的 `brotli_static on;`）。
- **约束**：`release-cache-manifest.json` 记录的是解码后响应体的大小和 SHA，预压缩只改变传输编码，Service Worker 缓存的是解码后的内容，与清单一致；`.br`/`.gz` 文件本身不进入清单。
- **验收**：首次访问的传输字节下降；Viewer 缓存 smoke（`scripts/smoke-published-cache.mjs`）通过。

### LD8（P0）GI 资源有界并行加载

- **位置**：`lightingRuntimeResources.ts:68-85`（`for ... await` 串行读取、校验、解码）。
- **方案**：用并发上限为 4 的队列并行执行 读取 → SHA 校验 → 解码；纹理解码改用 `createImageBitmap(blob, { imageOrientation: 'flipY', premultiplyAlpha: 'none', colorSpaceConversion: 'none' })` 后上传（必须保证 RGBM 的 alpha 不被预乘，翻转方向与原 `invertY` 一致）。保持“全部资源验证完成后才返回候选集合”的原子语义，以及取消和失败时的释放逻辑。
- **验收**：多图集场景 GI 加载耗时下降；取消、校验失败、解码失败测试全部通过（`test:lighting-optimization`、`lightingTextureFailure.test.ts`）。

### LD9 全量同步分批

`refreshing-scene-models`（60 s）和打开关键路径统一归入 P2-R3，本文不另立方案；R3 落地时可结合 LD5/LD6 的预编译与对象池。

## 6. 渲染

### R1（P1）GPU 能力分级与画质档

- **方案**：首次启动时用以下信息判定 T0/T1/T2，并缓存结果：`engine.getGlInfo().renderer`、`getCaps()`（`maxTextureSize`、`maxTexturesImageUnits`）、以及一次短时离屏基准测试（固定场景渲染 N 帧）。
- **用途**：只用于开启增强档（S3、L10），以及在管理器中给出建议。默认值不变，不因为判定为 T0 就自动降低画质（降低画质属于档位 B，需用户显式选择）。
- **验收**：判定结果写入诊断报告；在不同显卡上的判定合理。

### R2（档位 B，默认关闭）编辑器空闲降帧

- **方案**：同时满足以下条件超过 N 秒时，把帧率降到 10–15 fps：无指针/键盘输入、相机静止、无活动动画和动画组、MQTT 未连接或运行预览未开启、没有视频或大屏动态内容、没有加载任务。任一条件被打破立即恢复全帧率。
- **说明**：之前审计以“唤醒条件不完整”为由没有采用（第 16 节）。本方案把它作为显式选项，并列出完整的唤醒条件；运行预览和 Viewer 不启用。

### R3（P2，有条件）画布不透明

- **位置**：`createEngine.ts:402-409`（`alpha: true`）。
- **方案**：确认 Editor 和 Viewer 的嵌入场景都不需要透明背景（场景始终清屏为不透明颜色，宿主页面不透出）后，改为 `alpha: false`，可减少浏览器合成开销。只要存在需要透明的嵌入场景（例如中台 iframe 叠加），就保留现状，或做成 Viewer 运行配置项。
- **验收**：Editor、独立 Viewer、iframe 嵌入下截图一致。

### R4（P2，有条件）按脚本能力启用 `skipPointerMovePicking`

- **背景**：项目代码没有使用 `onPointerObservable` 或 `ActionManager`；之前否决全局启用，是因为外置脚本可能注册 Babylon 指针事件。
- **方案**：模型脚本预编译时扫描能力标记（是否引用 `ActionManager`、`onPointerObservable`、`pointerMovePredicate`、`meshUnderPointer`、`enablePointerMoveEvents`）。当前场景所有已加载脚本都不使用这些能力时，才设置 `scene.skipPointerMovePicking = true`；加载到使用这些能力的脚本时立即恢复为 false。
- **收益**：中等偏低（省去每次指针移动时的全网格遍历），作为低风险附带项实施。

### R5（P2）大网格场景使用 GPU 拾取

- **背景**：单个网格达到数十万三角面时，CPU 射线拾取与多重拾取（`ScenePickingAndSelectionController.ts:85/136/168/312`）的点击延迟明显。
- **方案**：先核对 Babylon 9.12 是否提供 `GPUPicker` 及其对薄实例的支持。若支持，为点击选择提供 GPU 颜色 ID 拾取，并保留 CPU 拾取作为精确兜底（例如需要 faceId 的场景）。
- **验收**：点击延迟下降，选中结果与 CPU 拾取一致。

### R6（档位 B / P3）遮挡剔除

- Babylon 的逐网格遮挡查询（`occlusionType`）有一帧延迟，会产生“弹出”现象。只建议对厂房内部的大型分区（墙后整片区域）以分组方式试验，默认关闭。

### R7（档位 B）LOD

- 支持 `MSFT_lod` 或作者提供的多级模型，或由 LD2 的 B 档生成简化级别，用 `addLODLevel` 挂接。脚本模型的节点名必须保持不变，否则不能使用 LOD。默认关闭。

### R8（档位 B）相机运动时自适应分辨率

- 相机移动期间临时调高 `hardwareScalingLevel`（例如 1 → 1.25），静止后立即恢复为 1。对 4K 下 T0 的 GPU 填充率有明显收益。默认关闭。

### R9（P2）冻结覆盖率审计

- 环境已经冻结世界矩阵和材质。在性能报告中增加“静态网格中未冻结矩阵/材质的比例”统计，找出可以安全冻结但被遗漏的类别（例如没有脚本的静态普通模型实例）。逐类评估，必须配套精确的解冻路径，禁止全局冻结。

- 出现任何正确性回归（资源身份、拾取、阴影、GI 失效、设备轨迹）时，先回退该项再定位。

## 9. 已否决 / 不建议项

| 项目 | 原因 |
| --- | --- |
| 直接把动静合批设为默认 | 实测 FPS 为负收益（−38%～−50%），由 P2-R4 有条件研究 |
| 全局 `scene.freezeActiveMeshes()` | 会阻止脚本、动画和设备动作的可见性更新 |
| 为提升 FPS 丢弃或合并 MQTT 中间消息 | 中间消息包含取放货、故障等边沿事件 |
| 未经作者声明自动推断脚本纯度 | 现有实验在实际工厂中覆盖率为零（见光照失效结果） |
| 默认降低 DPR、纹理质量或阴影质量 | 违反主路线契约，只能作为档位 B |
| 重复建设天空盒 Worker、模板缓存、空间分片、碰撞索引 | 已经存在并在使用 |
| 截断 RGBM 动态范围以提升精度 | 违反“不夹断数值”的约束，改用 B8 的 gamma 编码 |
| 改写参数化脚本内部或设备驱动算法 | 受保护实现，只优化外围 |
