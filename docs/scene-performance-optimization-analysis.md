## 1. 核心结论与问题定性

### 1.1 核心问题定性
在 NVIDIA RTX 5060 独立显卡环境下，场景出现 **平均 30 FPS、最低 2.08 FPS、P95 帧时间 452.9 ms** 的严重卡顿，其根本原因**不是 GPU 算力不足或显卡驱动异常，而是 CPU 主线程被高频长时间任务（JavaScript Long Tasks）100% 满负荷打满**。

现场捕获到两组关键的反差数据：
1. **GPU 渲染极快**：在帧率暴跌至 2.08 FPS 期间，Babylon 内部每帧实际的 GPU 画面渲染耗时（`renderTimeMs`）**始终仅为 10.8 ~ 12.3 ms**（纯 GPU 理论帧率可达 80+ FPS）。
2. **主线程被严重阻塞**：在 60 秒的采样窗口内，累计捕获了 **84 次 Long Tasks，阻塞主线程长达 37,922 ms（约 38 秒）**。特别是在后半段卡死的 28.5 秒内，Long Tasks 累计高达 29,073 ms，导致浏览器事件循环极度饥饿，`requestAnimationFrame` 每 450ms 才能调度一次，从而将画面锁死在 2.2 FPS 左右。

## 2. 现有在途优化（2026-10-23-animation-frame-cost）评估

针对当前正在实施的两个优化点：
1. `filterTopLevelMotionNodes`：将运动节点祖先过滤从 $O(N^2)$ 改为 Set 线性查找；
2. `getLightingGeometrySignature`：增加弱引用快照缓存，减少网格/批次 dirty 时的 `Array.from()` 和数字哈希。

### 评估结论：
- **收益**：这两项优化逻辑严密、改动精准，确实消除了 512 候选节点时高达 78 万次的层级递归，也阻止了几千万顶点在重绘签名时产生巨大临时数组和 GC 停顿，是**非常优质的算法级防线，应当合并保留**。
- **局限性（无法根治现场 2 FPS）**：
  这两项优化单帧能挤出的 CPU 时间在 **5ms ~ 30ms** 量级。而现场面临的是：
  - **`展会货箱.glb` 首次解码耗时 6,032 ms（6 秒）的大停顿**；
  - **每秒发生 2~6 次、耗时高达 900ms ~ 2600ms 的连续长任务阻塞**；
  - **外置参数化脚本单个执行 1 秒（总耗时 13.4 秒）**；
  - **全场 5157 万顶点、3101 Draw Calls 的极端高模包袱**。
  
因此，**仅靠当前的动画帧开销优化，无法把 450ms 的单帧耗时拉回到 16ms（60 FPS）以内，必须针对核心诱因实施根治性措施**。

## 3. 现场卡顿的四大致命瓶颈剖析

### 瓶颈一：动态资产 `展会货箱.glb` 未做预热，解码耗时 6 秒直接打崩帧率
- **现场实测数据**：
  - 采样 0 ~ 26（前 48 秒）：画面稳定在 **61.8 FPS**，Long Task 为 0；
  - 采样 27 ~ 28：开始触发动态加载，`runtime.loading.active` 记录：
    `{"stage":"assetReadDecode", "fileName":"展会货箱.glb", "elapsedMs": 493.3}`；
  - 在 `runtime.loading.slowestAssets` 中：
    `"展会货箱.glb"` 的 `assetReadDecode` 单阶段耗时高达 **6,032.7 ms（6秒多）**；
  - 帧率随即由 44.7 骤跌至 17.0、8.5、4.0、3.2 FPS。
- **原因机理**：
  业务/仿真运行到第 28 秒开始产生货物时，系统才在主线程动态拉取和解码 `展会货箱.glb`。GLB 反序列化、网格实例化未经时间分片，直接导致主线程产生长达 6 秒的完全冻结。

### 瓶颈二：货物生成后缺乏“对象池（Object Pool）”，持续克隆诱发高频长任务
- **现场实测数据**：
  从采样点 38 到 59，`modelClone` 数量从 31 递增至 34（货物持续生成），每秒捕获 2~6 个 Long Tasks，每个采样周期累计耗时 900ms ~ 2600ms。
- **原因机理**：
  每次生成货物，系统都会触发完整的资产克隆、实体树构建、姿态与驱动绑定。主线程未对货物实体和几何做预分配池化复用，导致主线程在货物生命周期管理上持续超载。

### 瓶颈三：设备外置参数化脚本同步计算开销巨大（总计 13.4 秒）
- **现场实测数据**：
  `scriptInitialize` 累计执行 27 次，总耗时 **13,384.1 ms**。
  其中输送线电机（`EQ_GD有电机_修改.glb`）的 4 个实体：
  - `entity_8a5f8afe...`：耗时 **1,025.4 ms**；
  - `entity_f047a1cb...`：耗时 **988.6 ms**；
  - `entity_c1bdbd18...`：耗时 **926.3 ms**；
  - `entity_955ae68c...`：耗时 **879.7 ms**。
- **原因机理**：
  电机设备的参数化脚本中包含大量耗时的同步几何计算与拓扑构建，单脚本耗时就达到 1 秒，直接造成严重的主线程排队。

### 瓶颈四：开局准备与模型刷新耗时 60 秒（`refreshing-scene-models`）
- **现场实测数据**：
  - `scenePreparation.totalMs = 62,487.4 ms`；
  - `refreshing-scene-models` 占用了 **60,790.3 ms**；
  - `runtime.lastFullSyncDurationMs = 59,916 ms`；
  - 采样点 16（01:10:06）至 17（01:10:30）之间出现了长达 **23.4 秒的时间无响应空洞**。
- **原因机理**：
  启动全量同步（`fullSync`）是一次性同步推进的大量模型刷新，缺乏分批排队调度。

### 潜在炸弹：5157 万顶点与 3101 次 Draw Calls 的高模包袱
- **现场实测数据**：
  - `totalVertices`: 51,676,845（5167 万顶点）
  - `drawCalls`: 3,101
  - 抓取的高负载网格：`3d66-Editable_mesh-23255455-5580` 等道具，**单个尺寸仅 14cm × 14cm × 23cm 的小构件，顶点数就高达 293,123，面数 178,227**。
- **影响**：
  这些 3D 溜溜网高模小构件未做轻量化、未做合批，导致场景底层底色包袱极重。只要主线程发生轻微波动，系统便毫无缓冲空间。

## 4. 根治性优化实施路线图（建议行动清单）

### 第一阶段：P0 级攻坚（立竿见影，破除 2 FPS 锁死）

#### 1. 动态货物资产“启动预加载与预解码”（Preload & Pre-decode）
- **具体做法**：
  1. 在场景就绪（`SceneRuntime.sync()` 完成）或进场准备阶段，预先扫描场景内所有产生器（`modelGenerator` / `deviceSpawner`）可能用到的货物资产（如 `展会货箱.glb`）；
  2. 提前通过 `loadModelRuntimeAssets` 完成 GLB 读取与反序列化，将模板网格和材质缓存进 `sharedModelAssetCache`，并执行隐藏的预编译（Pre-warm）；
  3. **验收标准**：运行时仿真/产线首次吐出货物时，`assetReadDecode` 耗时从 **6032 ms 降为 0 ms**，消除帧率断崖下跌。

#### 2. 动态货物“对象池（Object Pool）”与 ThinInstance 复用
- **具体做法**：
  1. 废弃“产生一个货箱就 `modelClone` 一次、销毁就 `dispose` 一次”的旧模式；
  2. 预先分配固定容量（例如 30~50 个）的货箱实例池或静态 ThinInstance 矩阵槽位；
  3. 货物生成时，仅从池中取出一个空闲槽位，更新其位置矩阵（Transform）并设为可见；货物被输送机吸收或移出时，仅仅设为隐藏并归还对象池；
  4. **验收标准**：在连续货物生成和交接期间，`modelClone` 增量归零，**彻底消除每秒 900~2600ms 的 Long Task 连续阻塞**。

---

### 第二阶段：P1 级保障（消除秒级长任务，保障主线程健康）

#### 1. 外置参数脚本执行“时间切片（Time Slicing）”与限制
- **具体做法**：
  1. 改造 `scriptInitialize` 执行循环：在执行 `EQ_GD有电机_修改.glb` 等脚本时，设立单帧预算上限（如 12ms）；
  2. 当单次脚本执行超过预算时，通过 `await new Promise(requestAnimationFrame)` 或宏任务队列主动 `yield`，将剩余脚本分散到后续帧执行；
  3. **验收标准**：单个长任务时长不得超过 50ms，彻底消除 1000ms+ 的冻结。

#### 2. 场景启动全量同步（`fullSync`）分批化
- **具体做法**：
  1. 拆分 `refreshing-scene-models`（60 秒）：将数百个模型的初始化按可视距离、优先级划分，优先展示核心骨架，后代部件异步逐步呈现；
  2. 消除采样 16 至 17 之间 23 秒的完全失联。

---

### 第三阶段：P2 级固本（资产轻量化，卸下 5100 万面极端包袱）

#### 1. 3d66 溜溜网高模减面与烘焙（DCC 端）
- **具体做法**：
  1. 针对以 `3d66-Editable_mesh-23255455-5580` 为代表的 14cm 小型道具，在 Blender/3ds Max 中执行减面（Decimate），将单件 **29 万面降至 500 ~ 2,000 面**；
  2. 将全场景顶点数从 **5157 万压减到 300 万以内**；
  3. 合并小零件的材质和子网格，减少碎片化 Draw Calls。

#### 2. 扩展 ThinInstance 自动化合批覆盖率
- **具体做法**：
  1. 将场景中 3117 个离散网格中大量重复的托盘、支架、辊筒、横梁纳入 `modelArrayInstance` 批次管理；
  2. 将 Draw Calls 从 **3101 压缩至 300 以内**，释放数十倍的 CPU 绘图指令提交开销。
