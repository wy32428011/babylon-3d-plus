# 全项目优化方案（第二期）：进度盘点与突破路线

编制日期：2026-10-24
文档性质：持续更新的进度盘点与实施路线，最新核对日期 2026-10-25。第一期方案见 [全项目渲染光照烘焙加载优化方案](全项目渲染光照烘焙加载优化方案.md)，实施记录见 [第一期实施记录](tasks/2026-10-24-render-optimization.md)。历史工厂数字来自已有报告；本轮检查和单次真实 GLB 运输测量见 0.2，不能混作新的工厂性能结果。

## 0. 一句话结论

第一期的 Q0 已在本地验收通过；Q1 中能做到严格等价的部分也已交付。工厂场景（Intel UHD630、2560×1440、原 MQTT 回放）的 FPS 从约 5.7 提升到约 6.8，但卡顿依旧，P95 帧间隔约 415 ms。

在“对外置脚本和 Babylon 公开 API 的观察次数与顺序都严格等价”这一合同下，剩余的主线程工作大多是合同本身要求执行的。连续多轮内核级尝试（物化、memo、Set 惰性分配、字节比较展开、绑定失效归因）都没有可复现的净收益，并已按规则止损。

因此第二期分成两条路线：
- **不需要改合同、现在就能做的**：真实 GPU 计时、未覆盖场景的验证、打开耗时、无损资产治理、剩余严格等价的 Q2 项、工程收尾。
- **需要用户决策、但能突破上限的**：调整“观察次数”契约、模型脚本能力声明、外置 LED 脚本资产侧优化，以及档位 B 渲染选项。

**E1 修正。** 原文假设“Babylon 的 GPU 计时依赖 timestamp，所以拿不到”。核对 Babylon 9.12 `engine.query.pure.js` 后，此假设不成立：`canUseTimestampForTimerQuery=false` 时它已经走 `TIME_ELAPSED_EXT` 区间查询。新增探针 `scripts/probe-gpu-timer.mjs`（`npm run probe:gpu-timer -- --runtime browser|electron`）在真实 WebGL2 里直接发区间查询，读 `GPU_DISJOINT_EXT` 并丢弃无效样本。本机（RTX 2070 SUPER，ANGLE/D3D11）结果：Chrome 与 Electron 都可用，120 帧 120 个有效样本，disjoint 丢弃 0，`timestampBits=0`。这说明平台本身支持 GPU 区间计时。此前报告中 GPU 时间为 null，不能归因于运行时不支持；在 Intel UHD630 机器上该探针尚未运行，null 的原因仍未解释。下一步是在该机器上跑探针，并在真实场景里对照 Babylon 计数器是否取得有效值。

**N1/N2 验证与边界。** 新增 5 项用例（无消费者不收集且 dirty 保留、显式查询/调试预览/阴影开启后补收集、窗口内多次失效只收集一次、窗口随耗时放大且显式查询不受限、有 GI 状态不合并）。既有 59 项运行时用例在 `classificationCoalesceMinMs: 0` 的测试夹具下全部通过（它们验证“每帧立即消费”语义，夹具显式关闭窗口）；`test:lighting-bake` 251/251、`test:lighting-manager` 82/82、`test:lighting-unified` 42/42、`test:lighting-optimization` 79 通过 + 1 条可选跳过，`typecheck` 与相关文件 ESLint 通过。**收益尚未实测**：没有在工厂场景做 ABBA，预期方向是 getSources 次数与累计耗时下降（上限由窗口占空比决定），实际 FPS/长任务需按 P2-C 口径测量；窗口内新出现的网格在分类刷新前沿用“未分类按动态处理”的默认，最长延迟约一个窗口。

**N3 未做的原因。** 分类各来源单元并不独立（batch 优先占用、跨来源 used、可解析到其他模型的源节点），增量缓存需要依赖图与整场回退；D1 解除了“不能二次读取”的限制，可以先做影子模式（增量与全量并行比对）再切换，但实现面大，建议在 N1/N2 的工厂 ABBA 结果出来后，根据剩余 getSources 占比再决定是否投入。

**E4 实测（本机中台项目 2071816469849280514，23 个 GLB，79.9 MB）。** 全场约 90.2 万三角面，其中环境模型 `Env-2108165032203984898/model.glb` 占 86.7 万（96.1%），53.1 MB 且未压缩；设备模型都在 0.6 万面以下，未发现小尺寸高面数网格。结论：该项目的几何与下载体积几乎全部来自环境模型，优化重点应放在它身上，而不是设备模型。传输压缩实测：环境模型 gzip 后为原大小 80%、brotli 76%，全部 GLB 合计 79.9 → 64.8 MB（gzip）/ 62.7 MB（brotli），brotli 压缩 53 MB 约 9.5 秒。

**后续候选及已推进项：**
- LD7 扩展到 `.glb` 已在工作区实现：只改传输编码，解码后字节与 SHA 不变，收益不足 10% 的侧车跳过；本轮已补 HTTP 与缓存验证，实际项目样本及尚未通过的 Electron DIST 入口见 0.2。

**B4 暂缓。** 核对 `cycles_bake.py` 发现原假设有误：第二遍（隐藏灯光后的 direct）不只包含环境光，场景里带自发光的网格材质（`Emission Strength = 1`）也在这一遍贡献直接照明。因此“环境强度为 0 就可跳过”不成立，安全条件必须同时要求环境为零且没有任何非零自发光。此外本机没有 Blender，无法验证 Python 改动，故不修改。

**R3 暂缓。** 核对发现三处运行时（编辑器、Viewer、开场）的 `clearColor` alpha 始终为 1，`alpha:false` 理论上像素不变，但需要在 Editor、Viewer、iframe 嵌入三种宿主做截图确认，本次未做。

## 2. 当前预算与上限推算

数据来源：工厂冻结版 B 的 60 秒正式窗口。FPS 6.8167，即约 409 帧。CPU 数据来自 62.5 秒的采样包络。下面按帧平均是粗略换算，目的是估算量级，**不是收益承诺**。

| 预算项 | 采样归属 | 按帧平均（约） | 当前合同下能否压缩 |
| --- | ---: | ---: | --- |
| getSources（91 次/60 s，每次 282.7 ms） | 22.98 s | 56 ms | 严格等价下已见顶 |
| refreshSources 与绑定，扣除 getSources | 3.43 s | 8 ms | 同上 |
| camera/render | 16.50 s | 40 ms | 只剩必要工作，已诊断止损 |
| LED 外置脚本 observer | 5.09 s | 12 ms | 不允许改受保护脚本 |
| telemetry 与运动箭头 | 2.01 s | 5 ms | 不是主因 |
| GC | 2.95 s | 7 ms | 分配压力的结果，不单独优化 |

推算（只表示上限，实现后必须用 ABBA 实测）：

1. 如果分类工作从帧路径中基本移除（需要 D1 或 D2），每帧 CPU 约从 145 ms 降到 80 ms，CPU 上限约 12–15 FPS。
2. 如果在此基础上 LED 脚本的逐帧扫描也消除（需要 D3），上限约 13–16 FPS。
3. 剩余约 40 ms/帧的 camera/render，在 1,320 Draw、PBR 材质、T0 核显的条件下，主要取决于 Draw 数量和材质种类。要再往上，需要合批或减少 Draw（B10、档位 B）以及真实 GPU 计时（E1）来判断 GPU 是否成为新瓶颈。

结论：**在现有合同内继续做内核微调，期望收益已低于测量噪声**。第二期的主要收益必须来自 D1/D2/D3 这类合同级决策。

## 3. 无需决策、可立即推进的工作（E 系列）

### E1（P0）真实 GPU 帧时间测量

- **现状修正**：`canUseTimestampForTimerQuery=false` 不代表区间查询不可用，Babylon 9.12 已有 `TIME_ELAPSED_EXT` 回退。RTX 2070 SUPER 的独立探针可用；Intel UHD630 的空 counter 原因与工厂真实 GPU 分布仍需测量，不能把旧推断当结论。
- **方案**：在诊断构建中，用 `TIME_ELAPSED_EXT` 区间查询包住 `scene.render()`。区间查询不需要 timestamp 能力。每帧发起一次查询，延迟数帧读取，读取前检查 `GPU_DISJOINT_EXT` 标志，发生 disjoint 时丢弃该样本并计数。只用于诊断报告，不进入生产渲染循环。
- **价值**：判断去掉 CPU 瓶颈之后，T0 是否立刻变成 GPU 受限。这直接决定 D4 / B10 / 档位 B 的优先级。
- **验收**：工厂和至少一个小场景各取 60 秒的 GPU ms 分布，并记录 disjoint 丢弃率。若扩展在 Electron 中不可用，如实记为“不可用”。

### E2（P0）补齐未覆盖场景的验证

1. **中型 GI 场景**：选一个可在数十分钟内完成 CPU 烘焙的真实业务场景（不必是全厂），做 GI 开/关的 ABBA，测量 B6/B7/LD8 的实际加载耗时、代理数量、Draw Call、JS 堆和缓冲字节。这是 B10 是否值得做的前提。
2. **工厂 Viewer 路径**：给出两种可选做法，由用户选择（见 D5）。其一是后台完成一次全厂 CPU 烘焙（耗时长，需要专门安排时段）；其二是在工厂副本上把 `bake.enabled` 设为 false 后发布，只验证 Viewer 的非 GI 路径（这改变了场景配置，必须标注为不同条件）。
3. **展会场景复测**：在独显机器可用时，用同一套 ABBA 工具测量第一期的全部收益，同时完成 R1 的 T1/T2 阈值校准和 B2-GPU 实测。

### E3（P1）打开耗时（对接 P2-R3）

- **现状**：展会样本中 `refreshing-scene-models` 耗时 60.8 s、脚本初始化累计 13.4 s（单个电机脚本约 1 s），中台冷/暖打开约 84–96 s。第一期没有专门处理打开链路。
- **方案**：按 P2-R3 用同一打开 ID 串联主进程与 renderer 的关键路径 trace，产出“排队 / 下载 / 校验 / 解析 / 脚本 / 上传 / ready”七段的关键路径分解，再逐项处理：
  1. 每个脚本模型单独计 `constructor / onStart` 自耗时，按资源汇总前 20 名，交给资产作者（与 D3 的扫描器共用报告格式）；
  2. 复核外层 4 个资源并发、内层 4 下载 / 2 校验的实际峰值利用率，只在关键路径证明有空闲时才调整；
  3. 打开阶段的 SHA 校验如果在主线程，挪到 Worker 中执行（结果相同，只是换线程）。
- **验收**：冷/暖各 5 次交错对照，按 P2-C 口径报告；目标沿用 P2-R3。

## 4. 需要用户决策的突破路线（D 系列）

### D1（已批准，2026-10-24）调整“外部观察次数”契约

以下保留原决策背景；当前已按批准合同实施 N1/N2，仍保护数据值与有意副作用，N3 未开始。

- **原合同**：完整分类会读取外置脚本的 `dataDriven` 配置、运动 provider、节点和数组的 getter 与迭代器。原先要求这些读取的**次数、顺序和异常**都与原实现严格一致。这一条曾否决 L3（无消费者时不收集）、L4（增量缓存）、L5（合并窗口）、同轮 memo 等减量路线。
- **建议的新合同**：脚本**提供的数据值**和**有意的副作用**（修改场景、发出事件）保持契约；框架**读取配置的次数和时机**不再是契约（行业通常也不保证这一点）。脚本 getter 如果依赖被读取的次数，属于不受支持的写法，由 D3 的扫描器给出告警。
- **解锁的实施项**：
  1. **N1（L3 重启）**：没有消费者时不收集分类，消费者出现时同步补一次完整收集。
  2. **N2（L5 重启）**：连续失效在 250 ms 窗口内合并；管理器、烘焙、预检、定位类请求强制立即收集。依据是未分类的网格默认按动态处理，不会污染静态阴影缓存。
  3. **N3（L4 重启）**：按“模型单元”缓存分类结果。依赖关系按第一期设计文档列出的全局优先级处理（batch 优先占用、跨来源 used），不能处理的情况整场回退 full。可以先在影子模式下比较，因为合同已不再禁止第二次读取。
- **风险**：依赖读取次数的脚本会出现行为差异——上线前用 D3 扫描器筛查全部现有模型包。
- **验收**：工厂 ABBA 中 getSources 的累计耗时和长任务显著下降；分类结果、阴影角色、GI 失效行为和六姿态像素与原版一致；MQTT 按 source-t0 对齐后完整无缺口。

### D2 模型脚本能力声明（不改变全局合同的替代方案）

- 如果不接受 D1，就改为在模型包元数据中由作者**显式声明**。例如：

  ```json
  "runtimeCapabilities": {
    "lightingConfigStable": true,
    "sceneAccess": "self",
    "structureMutation": "none"
  }
  ```

- 只有声明了的包，才允许缓存其分类结果和配置读取；未声明的包保持现在的完整路径。这与第一期否决的“框架自动推断纯度”不同：可信度来自作者的显式承诺，加上 D3 扫描器的静态检查，而不是运行时推断。
- **代价**：收益取决于资产作者的覆盖率。工厂这类场景的主要模型都需要逐个复核后才能加上声明。

### D3 外置脚本资产侧优化与扫描器

- **扫描器（不改任何脚本，可以先做）**：对 `.model.ts` 做静态分析，标记以下写法：
  - 在 `onUpdate` 或 `onBeforeRender` 中遍历 `scene.meshes`、`scene.transformNodes`，或调用 `getChildMeshes`、`isDescendantOf`；
  - 每帧调用 `computeWorldMatrix(true)` 或 `getWorldMatrix().invert()`；
  - 每帧重绘 `DynamicTexture`；
  - getter 有副作用，或依赖被读取的次数。
- 扫描结果输出到模型库报告和 E3 的打开耗时报告。
- **LED 脚本（需脚本所有者同意，以新修订发布）**：工厂 LED 的 `getModelNodes` 每次都展开全场节点并调用 `isDescendantOf`。建议改为：
  1. 节点列表在 `onStart` 时缓存，模型结构变化时重建；
  2. 只有内容或滚动位置变化时才调用 `paintLedScreen`；
  3. 矩阵只在宿主移动时重算。
- 原脚本保留不变，新修订作为新版本，由用户选择升级。这不违反“受保护脚本不修改”：它是资产的新版本，不是框架偷偷改写。
- **预期**：LED 约 12 ms/帧的大部分可以消除（以 ABBA 实测为准）。

### D4 画质选项（档位 B 与画质修正）

以下各项一律是**场景或发布级的显式选项，默认关闭**，每项单独做截图和业务验收：

| 项 | 对 T0 的意义 | 画质影响 |
| --- | --- | --- |
| R8 相机运动时自适应分辨率 | 4K 下 GPU 填充率最大的杠杆 | 运动时略模糊，静止后恢复 |
| R2 编辑器空闲降帧 | 降低能耗和 UI 竞争 | 静态时无影响，需要完整的唤醒条件 |
| R7 LOD / MSFT_lod | 降低面数（展会场景 5,167 万顶点） | 远景细节减少；脚本模型节点名必须不变 |
| S4 小物体不投影、降低 PCF 档 | 减少阴影 pass 成本 | 阴影细节减少 |
| R6 分区遮挡剔除 | 减少厂房内部的 Draw | 可能出现一帧弹出 |
| L10 泛光时启用 MSAA | 画质修正，T1/T2 使用 | 边缘与关闭泛光时一致，GPU 成本增加 |
| B8 RGBM gamma 编码 | 修正暗部色带 | 暗部更准，像素有变化 |
| B9 光照图 mip | 远景不闪烁 | 远景外观有变化 |

先由 E1 判断 GPU 是否成为瓶颈：如果 T0 在 CPU 降下来后变成 GPU 受限，R8、S4、R7 的优先级上升；否则排在 D1/D3 之后。

### D5 工厂 Viewer 验证路径

二选一：全厂 CPU 烘焙（耗时长，需要专门时段），或者在副本上关闭 bake 后只验证非 GI 路径。

### D6 B10 GI 代理合并

如果 E2-1 的实测显示 GI 代理显著抬高了 Draw Call，再按第一期 B10 的设计做研究：按（材质, 图集）合并，三角面区间映射回实体用于拾取，选中描边单独渲染。这会改变公开的网格身份（例如脚本拿到的 Mesh 对象），在严格等价合同下不成立，需要先确认该合同在 GI 代理上可以放宽。
