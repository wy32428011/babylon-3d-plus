# 材质与光照烘焙、动静混合阴影

更新日期：2026-10-22。

天空盒的对象属性与场景属性继续管理 HDR/EXR 资源、旋转、分辨率及位姿；环境反射强度只读显示统一光照配置的当前值，点击“在管理器中调整”进入总览。照明强度统一由管理器设置，旧天空盒资源强度只用于历史场景迁移。

统一光照适用于厂房、货架、固定设备与运动设备共同存在的数字孪生场景。它把静态间接光和环境漫反射离线保存，保留运行时的直接光、材质高光、金属反射和动态阴影。“光照与烘焙管理器”是唯一配置入口；新版本不再提供旧 `baked/realtime` 模式选择、旧太阳阴影生成或主题自动接管灯光。旧场景经共享迁移器读取转换，照明和纯显示效果分别保存。

## GLB 标准预览与默认环境照明

新建场景默认自带与 Babylon Sandbox 相同的 San Giuseppe Bridge 预过滤环境，旋转约 317.42°、强度 1；保留原有可编辑主光、补光与其它默认设置，让使用 StandardMaterial 的立方体等基础对象继续可见。显式应用“GLB 标准预览”后，才关闭额外主光、补光、阴影、间接光烘焙应用、昼夜控制和显示调色。普通模型与环境模型共用场景照明，不改 GLB 底色、金属度或粗糙度。环境模型应保持 100% 透明度做保真对照。

已有场景打开时沿用保存的照明和外观，不自动切换。需要对齐时，打开“光照与烘焙管理器”→“总览与烘焙”→“场景照明”，在“光照预设”选择“GLB 标准预览（对齐 Sandbox）”，再点击“应用配置”。该预设同时暂存照明与显示，一次撤销即可恢复；旧烘焙结果及其它计算参数保留，只关闭当前应用，重新启用时按输入签名检查是否过期。

“环境照明来源”可选择“场景天空盒”或“GLB 标准环境”；后者有独立旋转，并沿用“环境照明与反射强度”。缺少此字段的历史文件继续走场景天空盒。标准环境与背景资源独立，隐藏背景仍保留照明；保留但隐藏的背景加载错误不阻塞已就绪的标准环境，重新显示背景后仍会报告其实际状态。

环境文件及许可随 Editor 和 Viewer 构建离线打包，运行时不访问 Sandbox/CDN；保存、SOURCE 重开和 DIST 导出保留来源与旋转。标准预览默认不依赖 GI，后续可以按需要逐项启用灯光、阴影和烘焙。它对齐 Sandbox 的默认照明基线；若 Sandbox 中改过环境或色调映射，需要同步相应设置。

## 光照如何组成

| 内容 | 处理方式 |
| --- | --- |
| 固定表面的间接漫反射、环境漫反射 | 编辑端使用本机 Blender/Cycles 计算，保存独立 UV、光照图集和探针资源 |
| 模型底色、法线、金属度、粗糙度等外观属性 | 按源材质参与烘焙计算，并保留运行时材质语义 |
| 直接光、高光与镜面反射 | 由运行时材质继续计算 |
| 静态物体的遮挡 | 缓存静态阴影深度；投影、光源或相关几何变化后更新 |
| 运动物体的遮挡 | 实时更新，并与静态遮挡共同作用于直接光 |
| 运动物体的间接光 | 采样邻近光照探针；超出有效覆盖范围时沿用可用的基础照明 |

静态物体仍可遮挡运动设备，运动设备也可把阴影投到静态环境和其他运动物体上。阴影合成与间接光、反射分别处理，避免把整个最终颜色反复压暗。

旧“静态烘焙（FPS 优先）”的生成、结果应用和发布准备链已经退出。旧太阳阴影只记录环境表面的遮挡或颜色，不能作为新的间接光图集、独立几何和探针结果使用。环境统一参与场景照明，旧“保持环境原貌”的受光隔离不再作为另一条渲染路径。

## 打开集中管理器与开始烘焙

Toolbar 的太阳形按钮“光照与烘焙管理器”是统一入口，不依赖当前选择。场景 Inspector 的“光照与烘焙”保留状态摘要和“打开管理器”；模型或对象 Inspector 的“烘焙与阴影”保留静态、动态、待检查及配置来源摘要，点击“在管理器中定位”会进入对应对象范围。Inspector 和 Project 资源库点击/拖入不再直接写旧主题光照配置。

管理器有四个页签：

| 页签 | 用途 |
| --- | --- |
| 总览与烘焙 | 设置场景照明、显示效果、阴影和烘焙质量/预算，暂存光照或显示预设，查看真实 Scene 快照及上次结果，开始或停止运动预览 |
| 分类规则 | 设置场景默认，按模型资源、设备类型、场景分组或全场景建立可复用规则，查看影响范围与已有例外 |
| 对象与部件 | 搜索、筛选和分页查看实际生效值及来源，集中暂存对象或稳定部件的例外，并在场景中定位 |
| 任务与资源 | 查看后台任务进度、失败原因、已保存资产清单和失配诊断，取消任务或清除结果关联 |

完成一次混合光照配置与烘焙：

1. 加载工程，等待实际模型、参数几何和环境准备完成，再打开管理器。
2. 在“总览与烘焙”设置场景照明：选择“统一主光”或“场景方向光”，调整补光与环境反射，核对各场景灯是否参与照明。再设置阴影、静态缓存、动态阴影、间接光烘焙及质量参数；距离与偏移等位于“高级阴影设置”。
3. 在“分类规则”设置可复用策略；在“对象与部件”核对有效分类、配置来源和影响范围，按需暂存例外。
4. 点击“应用规则”或“应用配置”。本次草稿整体校验后，以一次可撤销更改提交；仅修改过的字段和对象参与更新。需要立即烘焙时，可以使用“应用并烘焙”。
5. 在没有待应用草稿时点击“开始烘焙”或“重新烘焙”，到“任务与资源”查看准备、烘焙和应用进度。结果通过校验并成功应用后才提交新资产关联。
6. 在总览或任务页检查结果状态、图集、探针、纹理字节和耗时，再保存场景。

页签切换保留本地草稿，不立即改变场景。关闭时有未应用内容，会要求继续编辑或明确放弃；关闭管理器不会取消已经运行的后台任务。若场景在其他操作中发生更新，旧草稿会保留并阻止覆盖提交，需要重新载入当前设置。运行预览或烘焙进行时配置只读，仍可停止预览、查看任务或取消烘焙。

除同时暂存照明与显示的“GLB 标准预览”外，其它“光照预设”只暂存主光、补光、环境反射和阴影浓度；“显示预设”只暂存背景、天空盒显示、曝光、色调映射、对比度、光晕、泛光和雾。两者不会立即写盘，也不会恢复旧主题对业务灯光的隐式接管。预设、手动参数和分类例外都通过同一个“应用配置”事务提交；普通配置草稿不能替换、伪造或清除烘焙资产关联。

“启用阴影”控制实时投影和缓存，不控制主光、补光或环境反射的生灭。选择“场景方向光”时，统一主光的颜色、方向和强度控件不参与当前照明；现有实体灯通过“参与照明”列表显式启停，不修改其业务实体可见性。修改曝光、对比度、雾和背景等显示效果不会使 GI 过期；改变实际主光、补光、环境反射或参与照明的灯光会改变 GI 输入。

“允许昼夜循环控制光照”对应 `allowDayNightCycle`。旧主题原本屏蔽日夜控制，迁移时保留为关闭；没有旧主题的场景默认允许，用户可以明确调整。实际活动的日夜控制器会持续改动灯光，开始烘焙前须先暂停控制器或关闭该允许开关并应用配置；停止运动预览不等于已经暂停所有日夜光照控制。系统不会静默冻结业务周期后宣称烘焙输入稳定。

显式应用标准预览后关闭阴影和烘焙应用；新建场景保留原有阴影与烘焙默认选项。需要烘焙时，计算参数默认是标准质量、2048 图集、32 像素/米、4 米探针间距、256 MiB 贴图预算，静态遮挡缓存和动态阴影的选项保留。提高纹理密度、减小探针间距或提高质量会增加计算与存储开销。贴图预算和结果中的纹理字节不代表整个场景的总显存占用。

纹理密度按世界空间中的实际尺寸计算，非均匀缩放和镜像也参与展开。单个大网格可自动切分为多个接收片并跨多张图集，结果中的表面数因此可能大于源网格数。系统不会为通过预算而自动降低密度或丢弃几何；空间切分、UV 岛间距与装箱留白也会影响最终图集数量。

当前图集不生成 mipmap，结果中的纹理字节按“图集张数 × 图集尺寸² × 4 字节”计算，与 PNG 的磁盘文件大小不同。预算不足会保留旧结果并明确失败；完成装箱后，错误信息会给出所需图集数量和 MiB。需要时明确调整预算、密度或图集尺寸后重新烘焙。

若按已应用配置判定没有需要烘焙的静态接收表面，管理器会显示“无需静态烘焙”，可继续使用原生实时照明和动态阴影并发布，不启动空的 Blender 任务。自动分类模型可能包含固定部件；环境也参与规则解析，仍需以完整实际来源核对范围。

## 分类规则、部件策略与已有例外

分类规则保存在当前场景。模型资源规则按实际解析出的资源身份或精确资源位置匹配，普通模型、组合成员、生成输出、逻辑阵列和原生薄实例共用这套解析；环境可以按“环境”类型或实际环境资源设置。为同一资源配置一次后，当前匹配实例与后续新增匹配实例都会继承。模型名称相同、设备名称包含某个词，不构成资源或运动类型匹配依据。

每条规则可分别设置“动静分类”“投射阴影”“接收阴影”“参与间接光”。优先关系按字段解析：

- 列表上方的匹配规则优先；标为“继承”的字段继续寻找下方规则。
- 同一规则内，匹配的部件策略先于该规则的对象默认策略；部件策略也可排序。
- 没有规则提供的字段使用场景默认；“自动”使用真实运动驱动、动画、层级和脚本证据。
- 已有对象例外和部件例外继续保留，部件例外优先于对象例外。创建或调整场景规则不会自动抹去这些配置。
- 真实动态祖先的约束始终有效。静态例外不能抵消父级运动，静态标记也不会冻结原有脚本、动画或设备动作。

“固定结构”“运动部件”策略使用实际驱动解析出的角色。仅有状态遥测不等于几何运动；自动判断时，未知脚本运动范围会保守按动态处理，明确只生成固定几何的参数模型可以静态参与。需要指定具体部件时，使用当前资源内的稳定节点键和资源身份。资源修订、参数几何或拓扑变化导致绑定失配时，该部件策略保留供检查，但其值不会套到新资源的同名节点；核对后重新选择有效节点或删除失配策略。

“对象与部件”展示实际生效值和逐字段来源，可按资源、类型、分组、分类或来源筛选，再搜索、分页和批量选择。普通对象及真实场景逻辑阵列实例可单独设置例外；锁定对象只能查看。批量栏中的“保持原设置”不修改该字段，“继承规则”恢复所选层的继承关系，“暂存例外设置”先更新草稿，页脚应用后才生效。“恢复规则”解除所选对象或部件这一层的例外；若对象层仍有例外，部件恢复继承后仍受它影响。

旧场景已有 `components.lighting` 会按原有四字段例外保留。希望让新规则接管时，需明确逐字段恢复继承，或恢复对应对象的规则继承；不会仅因打开管理器就重置旧配置。

运行时临时生成的货物或组合部件没有稳定的场景实体 ID，只能查看、选择和定位，不能把单个临时部件例外写入设备宿主。请在对应资源或类型规则中配置部件策略。真实存在于场景文档中的宿主整体仍可编辑；真实逻辑阵列实例保留自己的实体 ID，可继续逐实例设置。环境没有普通实体例外，应使用集中分类规则。

界面影响范围来自当前实际加载的来源；尚未就绪的模型会提示等待，未加载资源不会伪装成已经解析出的部件。可编辑宿主对象数与运行时生成实例、部件数并非同一计数。“查看影响对象”会进入对象页；模型 Inspector 的“在管理器中定位”和对象页的“在场景中定位”可帮助核对具体来源。

## 真实 Scene 快照与运动预览

总览中的“场景预览”是当前主 Scene、当前已应用配置的真实视口快照，不创建第二个场景，也不代表未应用草稿的渲染效果。应用草稿后可点击“刷新场景预览”；“正常材质”“分类预览”和“查看烘焙前”用于临时对比，关闭管理器后恢复其接管前的显示状态。

“运动预览”沿用现有运行预览与 MQTT 预检，不改变设备动作、参数脚本或消息语义。有草稿时应先应用，预检不满足时会显示原因。管理器内仍是可刷新的快照；启动运动预览后，关闭管理器可在主 Scene 完整观察真实运动，再通过既有运行控制或总览中的“停止运动预览”结束。

烘焙与运动预览互斥；旧太阳阴影任务已经移除。分类颜色、定位请求和烘焙前对比均为会话状态，不写入场景或撤销历史。

## 材质、透明度与支持边界

物理材质的 opaque、mask、blend、基础色贴图的 alpha 和已启用的顶点透明度按实际材质语义导出。环境编辑面板的 `opacity` 属于编辑显示；调低它方便查看设备，不会把环境原始物理材质自动改成相同透明度。

当前材质导出覆盖 `PBRMaterial`、`StandardMaterial` 及由支持材质组成的多材质；自定义着色器材质不在通用支持承诺内。

实际使用独立透明度贴图 `opacityTexture` 的材质，需要先把透明度合入基础色 alpha，或取消该表面烘焙。当前 Cycles 导出也不支持 U、V 使用不同纹理寻址模式；遇到这些情况会明确报告原因并保留旧结果。

当前材质纹理捕获使用 PNG 数据。浮点材质纹理出现超出 `[0, 1]` 的值或非有限值时会明确拒绝，不通过夹断数值伪造成功。HDR/EXR 环境照明使用独立的环境通道，不能据此推断任意 HDR 材质贴图也已经支持。

实时混合阴影覆盖方向光、点光源和聚光灯。矩形面光可按离线引擎能力参与间接光计算，但不能据此认为它具备与点光、聚光相同的实时投影能力；半球补光也不生成直接投影。实际灯光数量、材质采样器和阴影质量仍受 Babylon 与显卡预算影响，不承诺无限灯光、固定 FPS 或所有面光投影。

静态深度缓存需要 WebGL 2。正常的多个 rendering group 共用同一灯光面或级联的静态缓存，各组动态遮挡继续累积。对显式改变阴影图组间深度清理规则的定制渲染目标，保留原生完整实时路径，并在运行时诊断中记录原因。

独立烘焙 UV 不占用源材质原有 UV。多材质、阵列和原生薄实例需要保留实际几何与逻辑实例身份；遇到不支持或不完整的材质、几何、贴图时，任务应报告具体原因，保留旧有效结果。

## 取消、过期与清除

- 准备、烘焙和应用阶段都可取消。只有仍属于当前 request、输入未变化且产物校验通过的结果才能提交。
- 取消、引擎失败、资产读取失败或应用失败不会把半成品替换为有效结果；旧结果及其资产保留。
- 修改静态几何、参数、材质、参与分类或实际光照输入后，需要重新烘焙。主光、补光颜色/强度、环境反射强度及获准的日夜控制配置进入输入签名；纯外观、实时阴影质量/距离/偏移和缓存开关不进入 GI 签名。运行时动态设备的移动不会因每帧姿态变化而触发静态 GI 重烘焙。
- 结果签名过期时显示“已过期”；撤销修改并成功恢复原结果后回到“可用”，同时清除已恢复的运行时错误。真实烘焙任务的失败原因不会被正常的运行时状态轮询抹掉。
- GI 发布准备按实际任务进度与取消信号等待；后台有独立的取消和超时处理。
- “清除烘焙结果”解除当前场景的结果关联。为支持撤销、重做和其他场景引用，已生成的任务资产不会因此立即物理删除。

## 保存、迁移与发布

新场景文件外层版本为 `6`，新版编辑器继续读取 version 1–6；新文件需要配套新版编辑器和 Viewer，旧播放器不能按缺省旧阴影模式解释它。文件版本与以下配置版本是不同层次：

本地打开、已配置中台的资源准备、SOURCE 工程包和发布预检统一使用 `electron/shared/sceneFileVersion.ts`。未知版本、字符串版本会明确拒绝，光照资源预处理不会先将它们改写为 6。更新主进程后需要重新启动编辑器，已运行窗口不会自动载入新的主进程代码。

| 保存位置 | 内容 |
| --- | --- |
| `sceneSettings.lighting`，version 2 | 主光 `main`、补光 `fill`、环境反射 `environmentIntensity`、显式禁用灯列表 `disabledLightIds`、日夜控制 `allowDayNightCycle`、实时阴影 `shadows`、烘焙 `bake`、分类规则 `policy`、结果清单 `result` |
| `sceneSettings.appearance`，version 1 | 背景、天空盒可见性、曝光、色调映射、对比度、光晕、泛光与雾 |
| `components.lighting` | 对象及部件例外，字段级继承仍由 `inheritPolicy` 区分 |

旧 `theme`、`shadows`、`lightingBake`、`lightingPolicy`、`lightingBakeResult` 仅供共享迁移器兼容读取，新保存删除这五项旧字段，只写统一结构。已经存在的新配置优先，不和旧值拼成第二套设置。未知扩展数据、实体、材质、动作和规则保留；不能把“组件缺失、恢复继承”误读为渲染宿主的旧例外。旧主题原本关闭的方向光/半球灯转为显式禁用状态，避免移除主题后突然叠加照明。

读取旧场景只在内存中转换，不自动覆盖原文件，不自动启动 Blender。第一次保存覆盖旧格式文件前，会在旁边建立 `<原文件名>.before-lighting-v2.<内容摘要>.bak`，保存原始字节；同名备份只有内容完全相同才复用，备份失败或原文件期间发生变化时停止覆盖。另存为新路径不会替用户改写旧文件。

旧 `lighting-v1-*` GI 缺少证明实际填充光输入的完整戳，保留结果资源及原签名供核对，但转换后维持“已过期”，须用户明确重新烘焙。旧太阳阴影贴图不会升级成 GI。新 `lighting-v2-*` 结果也必须经过输入、资源身份和产物内容的严格等价校验；烘焙结果资产格式版本与输入签名版本不能混为一谈。

光照图 PNG、几何 JSON 和探针 JSON 位于工程的 `Assets/LightingBakes/<任务>/`。另存为会准备这些独立资产；目标同名文件只有内容一致才复用，不会覆盖不同内容的已有文件。

复制实体会保留其光照配置，但新增静态实体使原场景烘焙过期。撤销与重做不会删除已有资产。工程搬迁仅在输入、资源身份和产物内容等价时迁移签名；已经过期的结果不会因路径变化重新变为有效。

集中规则随保存、另存为、SOURCE 和 DIST 携带。仅按路径匹配的资源目标需要经过现有授权、复制及精确地址重写；即使没有 GI 结果，规则本身的本地引用也会处理。已经保存完整资源 `identity` 的目标，以该身份决定匹配；SOURCE/DIST 会移除不参与匹配的 `sourcePath`、`sourceUrl` 缓存提示，避免旧缓存已删除时阻断有效资源的发布。此处理只移除两项运输提示，保留规则顺序、值、资源身份、稳定节点绑定和其他扩展字段。

路径搬迁只能迁移等价输入的签名。规则值、目标身份或节点绑定发生实质变化时，已有 GI 按新的配置判定过期；不能通过重写 URL 或重新签名把过期结果变成有效结果。

发布时：

- 入口场景通过统一 GI 请求准备结果；非入口场景在隔离运行时中准备，全部使用新配置和相同校验，不再调用旧太阳阴影分支。
- SOURCE 携带可编辑场景和全部光照资产。
- DIST 携带 Viewer 所需的全部 PNG、几何 JSON、探针 JSON，重写资源 URL 并校验复制内容。
- 发布前的场景写盘与后续准备快照使用同一份迁移结果；取消、磁盘版本冲突或资源校验失败不能提交错误的候选场景。

**Blender 只在编辑端生成或重新生成结果时需要。** Viewer 读取已发布资产，不启动 Blender。部署包仍应通过 HTTP/HTTPS 静态服务器访问；不支持直接双击 `index.html`。

## 本机烘焙引擎

支持 Blender 4 或更新版本。引擎由本机环境变量、用户配置或标准安装目录发现，场景文档不能指定可执行文件。

当前后台使用独立的 Blender 进程与 CPU Cycles，不连接或改动已经打开的 Blender 会话及其偏好设置。历史混合光照流程曾使用 Blender 5.2.2；本轮统一配置的实测状态见任务记录，其他版本仍需按对应环境验证。探针数量上限为 4096，超过时会提示增大探针间距；后台任务默认最长运行 6 小时，可主动取消。超时和取消均不提交候选结果。

可在启动编辑器或独立 Cycles 测试之前设置实际安装路径：

```powershell
$env:BABYLON_BLENDER_PATH = 'C:\Program Files\Blender Foundation\Blender 5.2\blender.exe'
npm run dev:electron
```

也可在该应用的 Electron `userData` 目录放置 `lighting-bake-engine.json`：

```json
{
  "blenderPath": "C:\\Program Files\\Blender Foundation\\Blender 5.2\\blender.exe"
}
```

路径应替换为本机真实安装位置。引擎缺失、版本不支持或配置损坏会显示明确失败原因，不自动安装软件，也不把未执行的烘焙当作成功。独立 Cycles 测试使用临时目录，可通过同一个 `BABYLON_BLENDER_PATH` 环境变量指定引擎。

## 测试入口与证据

安装项目依赖后，按需要单独运行：

| 命令 | 范围与前置 |
| --- | --- |
| `npm run test:lighting-unified` | 覆盖统一配置、Store、原生光照与环境材质、首次覆盖备份及 SOURCE/DIST；不需要 Blender、浏览器或 GPU |
| `npm run test:lighting-manager` | 执行 5 个测试文件，覆盖策略解析、草稿事务、管理器视图模型、实际运行时来源及保存/SOURCE/DIST 迁移；不需要 Blender 或 GPU |
| `npm run test:lighting-bake` | 串行执行合同、分类、Store、保存迁移、SOURCE/DIST 文件链、运行时 manager 和阴影单测；不需要 Blender、浏览器窗口或实际 GPU |
| `npm run test:lighting-bake:cycles` | 先构建 Electron 代码，再调用真实 Blender/Cycles；覆盖生成提交、取消与超时、失败保留旧结果、共享图集逐面完整性、绕序与镜像、重复烘焙、大网格跨页、实际纹理密度及预算失败。缺少可用引擎返回非零，不记为通过 |
| `npm run smoke:lighting-unified` | 先构建 Viewer 和 Electron，以 `--unified` 运行真实场景照明/显示控件、规则和例外、Cycles、保存重开及正式 Viewer 流程；输出到 `output/lighting-unified/electron/` |
| `npm run smoke:lighting-manager` | 保留管理器范围的真实闭环，使用统一配置结构；先构建 Viewer 和 Electron，输出到 `output/lighting-manager/electron/` |
| `npm run smoke:hybrid-shadows` | 本机 Chrome/WebGL，检查静态与动态阴影像素、移动及缓存刷新；输出到 `output/playwright/hybrid-shadows/` |
| `npm run smoke:baked-lighting-material` | 本机 Chrome/WebGL，检查 PBR/Standard 的间接光、基础照明和反射叠加；输出到 `output/playwright/baked-lighting-material/` |
| `npm run smoke:lighting-bake-electron` | 先构建 Electron 代码及 Viewer 模板，再通过实际 Electron、Blender、GPU、临时工程和本地 MQTT 完成编辑及正式 Viewer 导出验收；独立 Edge 读取导出资源，输出到 `output/lighting-bake/` |

这些入口没有加入默认 core 组，耗时的 Cycles 与 GPU 检查不会随 `npm test` 自动执行。运行时单测使用 NullEngine，不能证明真实 GPU 像素、运动视觉或 FPS；文件链检查也不能单独证明 Viewer 渲染已经通过。保留的管理器及烘焙测试都按统一结构执行。当前检查数量、构建状态、实机结果和截图以对应输出及[统一光照任务记录](tasks/2026-10-21-unified-lighting.md)为准；[管理器历史记录](tasks/2026-10-20-lighting-manager.md)和[混合光照历史记录](tasks/2026-10-20-hybrid-lighting.md)不能替代本轮验收。本指南列出可执行入口，不预先宣称尚未完成的流程通过。

Electron smoke 保留可选工厂诊断：通过 `LIGHTING_FACTORY_SCENE_PATH` 指向本机实际工厂场景，以临时副本做 A/B/B/A 对照。该诊断停用外部遥测并阻断远程业务大屏及 HTTP 请求，保留屏幕占位；只放行固定版本 Draco 技术依赖，模型和环境就绪后才计时。新诊断使用同一统一光照路径，关闭 GI，仅比较静态阴影缓存关闭/开启，并采集帧时间和 Windows GPU 进程内存。它不执行完整工厂 GI，本轮统一配置切换也未因此取得新的工厂性能结论。性能采样须停止其他测试和构建；已有编辑端与 Viewer 验收证据时，可将 `LIGHTING_SMOKE_STAGE` 设为 `factory-only` 单独运行，输出到 `output/lighting-bake/factory-only/`。

已有当前统一配置流程实际烘焙并保存的主 smoke 临时工程时，可将 `LIGHTING_SMOKE_STAGE` 设为 `reopen`，复用有效 v2 Cycles 资产验证 Editor 重开、正式导出和 Viewer 三态。脚本读取原主报告，把场景复制到新的临时工程，只更换测试用本地 MQTT 地址，不重新生成光照图；报告写入 `output/lighting-bake/reopen/`。旧 v1 结果或其他轮次的历史通过记录不能替代当前验证。原临时工程缺失或 GI 已过期时需重新运行主流程，不能生成占位结果。

已有主 smoke 的真实保存重开及 Viewer 成功记录后，可运行 `node scripts/smoke-lighting-bake-state.mjs`，单独验证质量修改、过期显示、清除结果和两次 Ctrl+Z 恢复。脚本读取 `output/lighting-bake/electron-result.json` 中的原临时工程，在独立 Editor 会话中使用已有资产，不重新烘焙或写回原场景；五态报告输出到 `output/lighting-bake/state-result.json`。

统一光照对应的状态恢复检查使用：

```powershell
node scripts/smoke-lighting-bake-state.mjs --unified
```

该入口读取 `output/lighting-unified/electron/electron-result.json` 引用的已真实烘焙并保存的临时工程，通过管理器应用质量修改、查看过期、清除和撤销，复用既有 v2 资产，不重新调用 Blender。临时工程与资产必须仍存在；结果写入 `output/lighting-unified/state-result.json` 和本次状态检查目录。保留的 `--manager` 入口对应 `output/lighting-manager/` 报告，同样要求当前新结构下的有效结果。启动脚本不等于验收通过，应查看最终报告及退出状态。
