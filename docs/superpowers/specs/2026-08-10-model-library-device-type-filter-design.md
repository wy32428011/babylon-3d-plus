# 模型库按设备类型筛选设计

## 背景

数字孪生编辑器底部 Project 资源库的模型库已经支持按模型名称筛选，但模型数量较多时仍难以快速定位同类设备。现有模型包在 `meta.json` 的 `parameterScripts` 中通过 `deviceType` 描述设备类型，例如“输送”“多穿库”“货物”“RGV”和“堆垛机”。

本次在不改变模型包格式、资产索引版本和现有外部行为的前提下，为模型库增加基于 `deviceType` 的类型筛选。

## 目标与验收条件

### 目标

- 在模型库名称筛选旁增加模型类型下拉框。
- 从已经加载的模型资产元数据中提取可用的 `deviceType`。
- 支持名称与模型类型组合筛选。
- 保持其他资源库 Tab、模型导入、模型同步、点击创建和拖拽行为不变。

### 验收条件

1. 模型库显示“全部类型”和当前模型资产中实际存在的设备类型。
2. 设备类型去除首尾空白、去重，并按中文顺序稳定排列。
3. 选择具体类型后，只显示 `deviceType` 完全匹配的模型。
4. 名称筛选与类型筛选同时生效，二者为 AND 关系。
5. 内置模型和未声明 `deviceType` 的导入模型在“全部类型”下显示，选择具体类型时不显示。
6. 切换资源库 Tab 或从场景实例定位模型卡片时，类型筛选恢复为“全部类型”。
7. 模型导入或数据中台同步导致当前选中类型消失时，筛选自动恢复为“全部类型”。
8. 无匹配结果时显示“未找到符合当前筛选条件的资源”。
9. 现有名称筛选、图片库扩展搜索和资源卡片交互不发生回归。

## 方案选择

采用“前端从现有资产元数据提取 `deviceType`”方案。

不在 `AssetEntry`、Electron IPC 类型或 `.babylon-editor/asset-index.json` 中新增字段，原因如下：

- 当前资产索引已经保存 `parameterScriptMetadata`，现有模型无需重新导入或重新同步即可参与筛选。
- 避免为了单一展示筛选修改主进程扫描、数据中台同步、索引兼容和拖拽载荷等多条链路。
- 类型提取可以封装为无副作用纯函数，便于独立测试；后续若业务需要把设备类型提升为正式资产字段，可以在不改变筛选交互的情况下替换数据来源。

不采用筛选时动态读取 `meta.json` 的方案，因为这会引入异步文件读取、权限和错误处理，并增加不必要的界面等待状态。

## 数据来源与类型提取

仅从模型库中的项目模型资产读取类型。内置基础模型没有模型包元数据，因此不生成类型选项。

对每个模型资产，按照以下顺序查找第一个非空字符串：

1. 遍历 `parameterScriptMetadata`，读取 `values.deviceType.value`。
2. 若未取得值，遍历同一脚本的 `fields`，查找 `key === 'deviceType'`，读取其 `defaultValue`。
3. 对结果执行 `trim()`；空字符串视为未声明类型。
4. 元数据节点不是预期对象、数组或字符串时直接跳过，不抛出异常。

`values` 优先于 `fields.defaultValue`，与模型包中“当前值覆盖字段默认值”的语义一致。

类型匹配使用去除首尾空格后的精确字符串比较，不做包含匹配或大小写折叠。当前设备类型主要为中文业务枚举，精确匹配可避免相似类型被误合并。

## 模块边界

新增一个聚焦模型库筛选的纯函数模块，职责包括：

- 从项目模型资产安全提取 `deviceType`；
- 从模型资产集合生成去重、排序后的类型选项；
- 判断资源卡片是否符合当前模型类型条件。

`ProjectPanel` 继续负责：

- 保存名称筛选和类型筛选状态；
- 组合名称条件与类型条件；
- 渲染筛选控件和空状态；
- 在 Tab 切换、场景模型定位和资产列表变化时维护筛选状态。

不把类型筛选逻辑写入 `ResourceCard`。资源卡片只负责展示和交互，不应感知列表筛选状态。

## 界面与交互

### 筛选行

模型库激活时，在现有模型名称输入框之后增加：

- 标签：`模型类型`
- 原生 `select`
- 默认选项：`全部类型`
- 动态选项：提取出的设备类型

其他资源库不显示模型类型下拉框，现有筛选行布局和导入按钮保持不变。下拉框采用与名称输入框一致的高度、边框、文字颜色和深色背景，并设置独立的无障碍标签关联。

### 组合筛选

筛选顺序不影响结果，逻辑统一为：

```text
名称匹配 AND（全部类型 OR 设备类型精确匹配）
```

名称为空表示不限制名称；类型为“全部类型”表示不限制类型。

### 状态重置

- 用户切换任意资源库 Tab 时，同时清空名称筛选并把类型恢复为“全部类型”。
- 场景实例请求聚焦对应模型卡片时，同时清空名称筛选和类型筛选，保证目标卡片不会被隐藏。
- 模型列表更新后，如果当前选中类型已经不在类型选项中，自动恢复为“全部类型”。

### 空状态

当名称或类型筛选处于启用状态且没有匹配卡片时，显示：

`未找到符合当前筛选条件的资源`

未导入普通模型包的原有提示仍保留。类型筛选不改变模型库始终包含内置基础模型的既有行为。

## 兼容性与范围控制

- 不修改模型包 `meta.json` 格式。
- 不修改资产索引版本或持久化结构。
- 不修改 Electron IPC 协议和数据中台接口。
- 不修改模型卡片点击、拖拽、导入、同步和场景聚焦协议。
- 不为环境库增加设备类型筛选；本次需求仅覆盖模型库。
- 不新增“未分类”选项。
- 不根据名称、目录名、脚本文件名或卡片副标题猜测类型。

## 测试与验证

### 纯函数单元测试

覆盖以下场景：

1. 从 `values.deviceType.value` 提取类型。
2. `values` 缺失时从 `fields[].defaultValue` 提取类型。
3. `values` 与 `fields` 同时存在时优先使用 `values`。
4. 非法结构、空白字符串和无类型元数据返回未声明。
5. 类型选项去空、去重并按中文顺序排序。
6. 选择具体类型时排除内置模型和未分类模型。
7. 名称与类型组合条件为 AND 关系。

### 回归验证

- 运行新增的数字孪生单元测试。
- 运行现有 `tests/digitalTwin/projectLibraryTabs.test.ts` 相关测试。
- 运行 TypeScript 类型检查。
- 检查最终差异，确认没有资产索引、IPC 或无关样式改动。

## 风险与处理

### 元数据格式不完整

类型提取函数使用防御式读取，任何非预期结构都按“未声明类型”处理，不影响模型卡片展示和使用。

### 同一模型存在多个参数脚本

按照元数据数组顺序读取第一个有效 `deviceType`。当前模型包把设备类型作为模型级信息，多脚本出现冲突属于模型包数据问题；本次不引入合并或冲突提示。

### 类型在同步后消失

资产更新后校验当前选择是否合法；失效选择自动恢复为“全部类型”，避免界面保持一个不可见的陈旧选项。
