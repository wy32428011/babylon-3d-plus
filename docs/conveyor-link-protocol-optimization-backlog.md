## 待办项

### 1. 偶发接力尖峰（嵌套级联）— 优先级低

**现状**：风暴治理后偶现单次接力 ~785ms（几十秒一次）：接力终点波触发新订阅、新订阅触发新接力，级联嵌套，单事件约 700 次派发。不掉帧、不卡死，仅理论上有单帧轻微卡顿可能。

**方案**：如要追究，先加 pushLog/store 写入计时确认每跳开销构成；根治手段为链路消息队列化 + 每帧限量派发（原 P1-5/P1-6），把嵌套级联摊到多帧。

**风险**：消息跨帧后引入顺序问题（taken 与二次交付的先后、跨帧状态一致性），是有代价的重构，实施前需先设计消息顺序契约。

### 2. 等待超时自动退订（原 P2-6）— 卫生项

**现状**：时空错配时 waitingTask 永不解除，链路登记长期挂满。治理后每帧成本近零，仅语义上"挂着"。

**方案**：waitingTask 超过 T 秒（建议取 staleAfterMs 的数倍）未被交付 → 自动 sendUnsubscribe + 清 waiting/pending，设备回到无货无等待态；下一个新 task 边沿重新判定。

### 3. transitedTasks 清理（原 P2-8）— 卫生项

**现状**：transitedTasks 只加不清，长时间运行缓慢膨胀（小字符串，内存压力极小）。

**方案**：随新 task 边沿只保留最近 M 条，或按时间超时清除。

### 4. 光电自愈刷出（原 P2-7）— 保真度决策，非性能项

**现状**：时空错配（数字孪生与真实产线非同时启动）时，真实货物物理在链上而孪生永远等不到，画面上中途接入的链段无货可见。

**方案**：设备 `front_has_goods=1`（入口光电有货）且本机无货且正在等待该 task → 判定真实货物物理在机上，直接在入口端物化货箱（等同起点刷出语义），孪生立即与真实产线自洽。

**决策点**：若接受"中途接入时链上货物暂不显示，等新 task 从起点刷出后逐渐同步"，可不做；若要求孪生随时贴近真实产线状态则值得做。实施后等待积累自然消解，待办项 2 基本不再必要。

已按签名门控落地：fields 未变化即跳过注入与阵列刷新。若实测仍有开销，残余手段：诊断写入的 2× JSON.stringify 同样按签名门控；字段比较改为浅比较替代每设备每帧 JSON.stringify。
